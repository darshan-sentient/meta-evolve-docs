    How Meta-Evolve compares¶

    This page answers a question new readers ask first: AlphaEvolve, GEPA's optimize_anything, and Meta-Evolve all run "propose, evaluate, keep the better one" loops — so what is actually different, and when would you pick each?

    Descriptions of external systems were checked against the linked primary sources on September 14, 2026. Their claims belong to those systems, and nothing here implies Meta-Evolve has reproduced their results.

    One sentence each¶

    • AlphaEvolve is Google DeepMind's discovery system: you bring a problem and an automated evaluator, and Gemini-written programs are selected by an evolutionary loop you do not operate yourself. Proprietary.
    • GEPA's optimize_anything is an open-source (MIT) optimizer: a strong reflective-mutation algorithm with Pareto selection, packaged behind a deliberately tiny API — a seed plus an evaluator.
    • Meta-Evolve is an open kernel: a programming model for building your own evaluated improvement loop out of replaceable parts, where every run leaves a durable, replayable, budget-exact record.

    All three run the same loop shape. They sell different layers of it:

                     AlphaEvolve   optimize_anything   Meta-Evolve
the results      product       headline            not yet demonstrated
the algorithm    internal      product             simple presets
the loop itself  internal      internal            product

    AlphaEvolve's product is the results (you rent the whole system). GEPA's product is the algorithm (the loop is fixed; you feed it). Meta-Evolve's product is the loop itself (you program it; the kernel guarantees the record).

    Side by side¶

    AlphaEvolve optimize_anything Meta-Evolve
    What it is Proprietary discovery system Optimizer library Loop kernel/library
    You provide Problem + evaluator Seed + evaluator Task, seed, proposer, search
    It provides Agent, search, compute Reflection + Pareto search Records, lineage, budgets, replay, seams
    Candidate form Code Text (string or named strings) Typed artifacts with codecs
    LLM proposer Built in (Gemini) Built in (your model choice) Not bundled; user-owned callable
    Loop internals Closed Selection configurable; proposal fixed inside optimize() Every stage replaceable
    Open source No Yes (MIT) Yes (Apache-2.0)

    What "control" means here, concretely¶

    Many frameworks are "flexible" through configuration flags. Meta-Evolve is different in a specific way: the loop is programmed, not configured. Each stage — proposer, evaluator, search program, context policy, artifact codec, workspace, storage — is a seam with a published contract and a conformance suite. You swap implementations, not flags.

    The practical payoff is ablation. Because a component can be replaced without touching anything else, you can run the identical task several ways under equal budgets and compare the records. The experience lesson does exactly that: the same task, proposer, search, and bounds across no-memory, push-only, pull-only, and combined runs. Push is declared as Experiment(context=...) and audited pull as Experiment(experience=PullAccess(...)); they are separate declarations, and PullAccess is not a context policy. Its transcript program:

    """Normalized transcript for progressive experience disclosure."""

from main import _edge_labels, _outcomes, run_experiment


results = run_experiment()
no_memory = results["no-memory"][0]
push, _ = results["push-only"]
pull, _ = results["pull-only"]
combined, storage = results["combined"]

print("repeated mistake:", _outcomes(no_memory))
print("no experience:", (no_memory.summary().primary_score, "off"))
push_usage = push.summary().experience_usage.context
print("pushed context:", (push.summary().primary_score, push_usage.records))
pull_usage = pull.summary().experience_usage.pull
print(
    "audited pull:",
    (pull.summary().primary_score, pull_usage.operations, pull_usage.records),
)
print("declared derivation:", _edge_labels(combined, storage))


    uv run python examples/learn/experience_reuse/learning_story.py
    Output
    no experience: (0, 'off')
pushed context: (10, 3)
audited pull: (10, 7, 20)

    That is a controlled experiment on the loop's own memory policy: one variable changed, everything else held. The same move works for search (Greedy vs BestOfN vs Population — see the policy comparison) and for proposers.

    A packaged optimizer exposes fewer of these seams. optimize_anything lets you choose the reflection model and configure candidate selection, including a custom selector, through GEPA's candidate-selection guide; the reflective proposal step and the loop around it are the product rather than replaceable parts. That is not a defect — it is the price of a two-argument API — but it means a question like "did the memory help?" is answered in Meta-Evolve by swapping one component and holding the rest fixed, and only partly answerable from inside a packaged loop.

    Control is half; the record is the other half¶

    Swappable parts alone would just be do-it-yourself. The second half is that whatever you plug in, the kernel still enforces the same invariants:

    • Independent evaluation. The evaluator measures the candidate outside the proposer's authority. A candidate cannot grade itself, widen its own budget, erase failures, or promote itself (architecture: authority boundaries).
    • Exact budgets. Seed evaluation, successor attempts, and experience access charge declared budget dimensions exactly, so "equal budget" comparisons are equal by construction, not by convention.
    • Lineage. Every successor names its parents; every decision-relevant observation is recorded at a logical time. run.lineage() is the exact causal chain, and proposers can declare which prior records they used through derived_from.
    • Replay. A durable run can be reopened and replayed to a byte-identical event stream (crash-recovery example). Stated precisely: replay reproduces the recorded run exactly; it does not re-execute a stochastic model. That is what a reviewer needs to check a claim, and it is the part most optimizer libraries do not attempt.

    Text-only optimizers also collapse artifact structure into strings: a candidate is well-formed only if the evaluator happens to reject malformed text at scoring time. Meta-Evolve artifacts are typed — source trees take exact-file patches through private workspaces, skill sets and harnesses have declared interfaces — and successors are validated against their parent before commit (add a domain).

    Where this sits on the self-improvement ladder¶

    The Last AI Built by Humans grades self-improving systems on five levels of autonomy and names three problems any credible claim has to answer. The map below is our reading of the shipped examples against that external taxonomy: not product tiers, not renamed APIs, and not a certification. The survey separates task-local output improvement from persistent system change, and merely saving a run establishes neither.

    Survey level Mechanism illustrated here What stays fixed or human-controlled Evidence and limits
    L1: execution Durable runs execute and retain a declared procedure Objective, procedure, acceptance, and reuse Versions and replay support retention; saved history alone does not demonstrate autonomous improvement
    L2: strategy Context, harness, and autoresearch examples vary candidate content within fixed tasks Fixture proposers or fixed rules author the proposals; evaluators, splits, limits, and promotion remain external Captured attempts and scores demonstrate the loop's shape, not model autonomy or transferable gains
    L3: experience acquisition Not reached Task and experience acquisition are externally prescribed Audited retrieval of existing records is not autonomous acquisition of new learning tasks
    L4: deployment adaptation Not reached Deployment and ongoing acceptance remain external No live adaptation lifecycle is demonstrated
    L5: meta-improvement Policy evolution evaluates a search policy as a versioned artifact Mutation choices, the interpreter, inner tasks, budgets, and evaluation are fixed Retained inner runs demonstrate a mechanism relevant to meta-improvement, not an automatic L5 capability claim

    The survey's three credibility problems are the invariants above, restated:

    • Safe inheritance. Version history, lineage, replay, and retained negative outcomes preserve what changed. The policy and harness examples also report successors that scored below the seed and per-episode held-out regressions. A zero on a fixture is not proof of sustained gains, safe inheritance, or transfer.
    • Autonomy attribution. Separate proposer, search, and evaluator roles let a record say which decisions were generated and which were fixed or human-owned.
    • Reliable verification. Independent evaluation, bounded access, and protected splits let a measurement be audited. Private selection still shapes the winner; only an untouched final split supports a separate check. None of this proves an evaluator correct or rules out every kind of overfitting.

    The examples demonstrate boundaries, not evidence that a model recursively improves itself. Critic evolution, the survey's open question about improving the verifier, stays in the research proposal, outside the shipped contract.

    What the others do better¶

    Honesty in both directions:

    • Call-site simplicity. optimize_anything is a seed and an evaluator. A first Meta-Evolve run asks for five declarations. For "make this prompt better this afternoon," the smaller API is simply the better tool, and the determinism ceremony here is friction with no payoff.
    • A strong proposer out of the box. GEPA ships state-of-the-art reflective mutation; AlphaEvolve ships a frontier coding agent. Meta-Evolve deliberately bundles no model — the shipped presets are simple, and the intelligence is whatever you connect at the proposer seam.
    • Demonstrated results. AlphaEvolve and GEPA lead with headline numbers. Meta-Evolve's examples are deterministic teaching loops; it has not yet produced a live optimization result of its own. Its claims are about the loop's guarantees, not about optimization performance.

    Choosing in practice¶

    • Improving one prompt or config quickly, cheap evaluations, nobody will audit the run → optimize_anything.
    • Algorithm discovery where you bring a problem and an evaluator and want the whole system run for you → AlphaEvolve, where you have access to it.
    • Controlled experiments on the loop itself (memory, search, proposer ablations), expensive or noisy evaluations where crash recovery and exact accounting matter, bi-level autoresearch setups, or any run whose record must justify a promotion decision → Meta-Evolve.

    Using them together¶

    These tools compose rather than compete. GEPA-style reflective mutation is, from Meta-Evolve's point of view, a proposer: a callable that reads the parent and prior evidence and returns a ProposalResult (SDK integration). Pareto-frontier retention is a search program behind the same contract as Greedy and Population (extensions). Hosted that way, the optimizer keeps its intelligence and the kernel adds lineage, budgets, and replay.

    The same seams make Meta-Evolve usable as a neutral harness for comparing optimizers under exactly equal budgets on identical records — a comparison no single optimizer can run on itself from the inside. Adapter compatibility with existing frameworks is the stated preference over duplicating their APIs; see OpenEvolve in the references.
