    Feedback Descent: improve a prompt from textual feedback¶

    Status: Experimental/live-only.

    Optional executable companion: open the canonical notebook. This chapter contains the full explanation; the notebook is not required.

    The concrete problem¶

    Who holds the all-time record at the Grammys for the most wins in the album of the year category?

    The solver receives this question and a noisy document bundle. It does not receive the evaluator's answer, gold URL, gold-document label, or the fact that this is the Feedback Descent development row.

    Two prompt candidates start from the same evidence:

    candidate A
Answer the question from the supplied documents. Return only the answer.

candidate B
Find the document that directly resolves the question, ignore conflicting
distractors, and return only the answer.

    The artifact being improved is the prompt itself, represented as meta.Text. The question, documents, exact-answer grader, and budget remain fixed.

    The idea¶

    Ordinary optimization says only “A scored 0 and B scored 1.” Feedback Descent adds an inspectable explanation of why one candidate is preferred, then asks an editor to derive a successor from that explanation.

    prompt A ──► answer A ──┐
                         ├─► pairwise preference + textual feedback
prompt B ──► answer B ──┘                 │
                                           ▼
                              edit preferred prompt
                                           │
                                           ▼
                                  evaluate edited prompt

    This lab isolates that mechanism. It does not implement the paper's full search strategy or claim to reproduce its results.

    From Meta-Evolve principles to this algorithm¶

    Feedback Descent sounds specialized, but the teaching loop is assembled from ordinary evaluated-improvement roles:

    Role Concrete component Why it is separate
    Mutable artifact Two seed meta.Text prompts, then one edited prompt The thing being optimized is explicit and immutable
    Task input Candidate-visible case.md Every solver receives the same question and noisy documents
    Proposal evidence Structured preference plus textual feedback The edit can name exactly what observation caused it
    Proposer Editor session constrained by EDIT_SCHEMA It may rewrite a prompt but cannot score it
    Evaluator Pairwise comparison session plus local exact grading Hidden answer and ranking stay outside prompt authority
    Search shape Compare two seeds, edit the preferred one once This is a fixed teaching schedule, not an unbounded optimizer
    Budget Five individually bounded sessions One bad step cannot trigger retries until improvement appears

    There is no numeric gradient. “Descent” means turning an evaluator's natural language diagnosis into the direction of the next artifact change:

    observed answer difference
  → evaluator says which behavior was better and why
  → editor converts that reason into a general prompt instruction
  → unchanged task measures the successor

    The algorithm is simple because Meta-Evolve already supplies immutable text, bounded provider sessions, structured evidence, typed failures, usage, and identity. The lab only has to specify who sees which files and how those five sessions connect.

    How the implementation moves data¶

    run() loads one full EvaluatorCase, but immediately renders only case.public for solver workspaces. _solve() combines one prompt with that public file and asks for the closed ANSWER_SCHEMA.

    PROMPTS[name] + public case
  ── _solve ──► SessionRecord(answer or failure)
  ── grade_record(expected answer, evaluator side) ──► Measurement

    Only _comparison_request() receives case.answer. It writes a private comparison.md containing the reference and both observed answers, then asks for COMPARISON_SCHEMA. That response is evaluator evidence, not a prompt artifact.

    The editor gets a new SourceTree with exactly:

    prompt.md    preferred seed prompt
feedback.md  comparator's textual feedback

    It cannot recover the hidden answer from those files. After schema validation, the code lifts value["prompt"] into a new meta.Text, rejects an empty or unchanged edit, records edit_derived_from="feedback.comparison", and calls the same _solve() and grade_record() path used for the seeds.

    This reuse is what makes the final comparison interpretable: the artifact is different, while public case, model, schema, grader, and bounds remain fixed.

    Walkthrough: one improvement cycle in four phases¶

    This walkthrough uses phase for an outer algorithm step. The five provider sessions inside the phases are five independent inner meta.run calls with Greedy(max_trials=1); they are not five search iterations.

    Phase Meta-Evolve components State entering the phase State leaving the phase
    1. Measure seeds Two immutable meta.Text artifacts; two solver SessionRequests; evaluator-owned grade_record() Prompt A, prompt B, and the same public case Two SessionRecords and two exact measurements
    2. Derive feedback Comparator request with COMPARISON_SCHEMA Both observed answers plus the evaluator-only reference Preferred seed name and textual feedback, or a typed failure
    3. Propose successor Editor request over a two-file SourceTree Preferred prompt.md and feedback.md; no hidden answer New meta.Text prompt with lineage to feedback.comparison
    4. Measure and retain Reused solver path and exact grader; LabResult Successor prompt and the unchanged public case Edited measurement, all session evidence, artifacts, lineage, and usage

    The authority boundary stays visible at every handoff. Solvers can answer but cannot grade; the comparator can read the reference but cannot edit the artifact; the editor can edit but sees only feedback; and outer Python decides whether a structured result is a measurement, a successor, or an unrankable failure.

    For a concrete state trace, suppose candidate B is preferred. No live outcome is being claimed here—the names show how records would flow:

    meta.Text(prompt B)
  + SessionRecord(candidate B answer)
  + SessionRecord(comparison feedback)
  ── editor request ──► meta.Text(edited prompt)
  ── unchanged solver/evaluator ──► Measurement(edited)
  ── retain ──► LabResult

    The five sessions¶

    # Session Observes Produces
    1 candidate_a solver Prompt A, public question and documents Structured answer A
    2 candidate_b solver Prompt B, identical public question and documents Structured answer B
    3 Pairwise evaluator Both answers and evaluator-only reference answer Preferred candidate and textual feedback
    4 Prompt editor Preferred prompt and textual feedback only Rewritten prompt
    5 Edited-prompt solver Rewritten prompt, original public question and documents Structured answer for exact grading

    The editor never sees the reference answer or gold URL. Its input is exactly the preferred prompt plus the feedback, so the successor can record:

    edited prompt derived_from feedback.comparison

    If the comparison or editor fails, later dependent sessions do not run. Five is the ceiling for one complete path, not a promise to spend five calls after a typed failure makes the remaining comparison meaningless.

    Structured evidence¶

    The evaluator must return this closed-world shape:

    {
  "preferred_candidate": "candidate_a",
  "textual_feedback": "A general explanation of what the prompt should change."
}

    preferred_candidate may be only candidate_a or candidate_b. Feedback must be non-empty, and extra fields are rejected. The independent validator runs for both live wrapper output and injected test output.

    The editor separately returns:

    {"prompt": "The complete rewritten solver prompt."}

    An empty or unchanged prompt is a typed ProposerFailure; it is not evaluated as if it were a new candidate.

    Minimal runnable mechanism¶

    The real implementation is deliberately small:

    from sealqa_labs import UserSdkSessionRunner
from sealqa_labs.feedback_descent import run

result = run(UserSdkSessionRunner(agent_factory=build_agent))

print("preferred:", result.artifacts.get("preferred"))
print("feedback:", result.artifacts.get("feedback"))
print("edited:", result.artifacts.get("edited"))
print("derived from:", result.artifacts.get("edit_derived_from"))
print("edited measurement:", result.measurements.get("edited"))
print("usage:", result.usage)
    Illustrative shape — live run, nothing captured
    preferred: <candidate_a-or-candidate_b>
feedback: <structured evaluator rationale>
edited: <complete rewritten prompt>
derived from: feedback.comparison
edited measurement: <exact metric or typed failure>
usage: <aggregated provider usage>

    Run it from a user-owned driver after authenticating your SDK:

    META_EVOLVE_LIVE_SDK=1 uv run python your_sealqa_driver.py feedback_descent

    The five sessions all use the pinned Haiku model, equal 50-turn ceilings, a 1,800-second adapter timeout, and a 1,860-second inner wall budget.

    How to read the result¶

    Inspect these fields in order:

    1. sessions: did every requested session succeed, and what did it cost?
    2. measurements.candidate_a and candidate_b: were the initial answers exact?
    3. artifacts.preferred: which prompt did the evaluator select?
    4. artifacts.feedback: is the explanation general, actionable, and grounded in the observed difference?
    5. artifacts.edited: did the editor actually change the prompt?
    6. artifacts.edit_derived_from: does lineage name the comparison evidence?
    7. measurements.edited: did the one edited evaluation improve, tie, or regress?

    Possible outcomes are intentionally broader than “success”:

    Outcome Honest interpretation
    Edited score improves The edit helped this one development case.
    Tie Feedback and editing bought no measured gain here.
    Regression The edit damaged this case; preserve the negative result.
    Comparison invalid There is no preference to rank or edit from.
    Editor unchanged No successor exists.
    Provider/timeout failure The attempt is unrankable, not a zero score.

    One development row cannot establish general prompt quality. A robust claim would require a separately declared held-out suite and repeated compatible comparisons.

    Leakage and validity checklist¶

    • Only the pairwise evaluator may read the hidden reference answer.
    • Neither solver request contains source URLs, split roles, or gold labels.
    • The editor workspace contains only prompt.md and feedback.md.
    • The edited solver sees the same public case as both initial solvers.
    • All solver arms use the same model and resource declarations.
    • A favorable edit is reported once; it is not selected from repeated reruns.

    Change and predict¶

    Remove “ignore conflicting distractors” from candidate B. Before running, predict:

    1. which prompt the evaluator will prefer;
    2. what general feedback it will produce;
    3. whether the edited prompt will improve, tie, regress, or fail;
    4. which evidence and lineage fields should stay unchanged.

    The interesting result is not merely the final score. It is whether the recorded feedback caused an inspectable prompt change under a valid comparison.
