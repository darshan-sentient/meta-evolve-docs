    EvoSkill: induce a reusable skill from recorded failures¶

    Status: Experimental/live-only.

    Optional executable companion: open the canonical notebook. This chapter is complete without it.

    The concrete problem¶

    One held-out question asks:

    How many airlines are members of IATA, the organization that supports airline activity and helps formulate industry policy and standards?

    The skill builder never sees that row. It receives experience from two separate induction rows, then the unchanged baseline and skill-augmented agents are compared on this and one other held-out row.

    The artifact being improved is a shipped meta.SkillSet: an immutable mapping from a path such as skills/sealqa.md to one inspectable Markdown document.

    The idea¶

    An EvoSkill-style loop turns concrete agent failures into reusable procedures:

    induction case 1 ──► recorded failure ──┐
                                        ├─► failure analysis ──► Markdown skill
induction case 2 ──► recorded failure ──┘                           │
                                                                    ▼
held-out case 1 ──► baseline vs skill-augmented comparison          │
held-out case 2 ──► baseline vs skill-augmented comparison ◄────────┘

    This lab separates three questions that are often blurred together:

    1. Did the baseline agent fail on induction cases?
    2. Did an analyzer actually read and generalize from those failures?
    3. Did the resulting skill help unchanged agents on held-out cases?

    From Meta-Evolve principles to this algorithm¶

    EvoSkill becomes a short composition once failure collection, proposal, and held-out evaluation are kept as different components:

    Role Concrete component Why it exists
    Episode runner _solve() using the common bounded session adapter Produces comparable answers or typed failures
    Evaluator Local grade_record() Keeps expected answers outside agent authority
    Experience Two EvidenceDraft induction records Makes prior failure observable without leaking gold answers
    Analyzer Pull-enabled session Chooses which prior records to inspect and generalizes patterns
    Proposer/builder Separate schema-constrained session Converts analysis into an inspectable skill artifact
    Mutable artifact Shipped immutable meta.SkillSet Versions the reusable procedure as ordinary Markdown
    Validation Two baseline/skill held-out pairs Tests transfer without reusing induction cases

    The “algorithm” is not hidden inside one giant prompt:

    run baseline episodes
  → grade externally
  → expose bounded failure evidence
  → analyze through audited experience pull
  → build a typed skill artifact
  → inject only that artifact into fresh held-out agents
  → compare each pair externally

    This is simple to build because Meta-Evolve already supplies SkillSet, experience grants, derivation, session accounting, typed failure, and immutable artifacts. The lab-specific code decides what a safe failure record contains and how the Markdown is inserted into the held-out instruction block.

    How records become a skill without leaking evaluation¶

    For each induction row, _solve() receives only its public case. Local grading then creates a Measurement. _failure_evidence() deliberately projects that full evaluator state into a smaller candidate-visible record:

    included: case_id, prediction, exact-if-valid, failure_kind
omitted:  expected answer, URLs, gold document, held-out content

    Those two records become seed_evidence in the analyzer's inner run. Because the analyzer also receives PullAccess, it must actively search/open them; the run records whether it did. ANALYSIS_SCHEMA forces separate failure_patterns and procedures, so the next step receives structured generalization rather than raw hidden evaluator state.

    The builder is a new session with only analysis.json. It cannot query the induction experience or inspect held-out rows. Its validated Markdown is lifted into:

    meta.SkillSet({"skills/sealqa.md": skill_markdown})

    For held-out evaluation, _solve() is reused unchanged. The skill arm differs only by appending the rendered skill to BASE_INSTRUCTIONS. This makes the skill artifact—not a model, case, schema, or budget change—the intended cause of any measured difference.

    Walkthrough: one improvement cycle in four phases¶

    The four phases describe the outer lab algorithm. The eight SDK sessions inside them are independent inner meta.run calls with one trial each, not eight optimizer iterations.

    Phase Meta-Evolve components Candidate-visible observation Retained evaluator result
    1. Record induction behavior Baseline solver requests; local grader; two EvidenceDrafts Each solver sees only its public induction case Predictions, exact-if-valid, and failure kinds; expected answers stay private
    2. Analyze bounded experience Pull-enabled analyzer request with meta.PullAccess Only the two projected failure records, read through audited pull operations Failure patterns, procedures, pull counters, or a typed failure
    3. Build successor skill Builder request; immutable meta.SkillSet analysis.json only; no raw experience or held-out rows One validated Markdown skill at skills/sealqa.md
    4. Compare on held-out rows Four fresh solver requests; reused grader; per-row comparison; LabResult Baseline sees base instructions; skill arm adds only the rendered skill Two independent comparison labels plus sessions, measurements, lineage, experience usage, and provider usage

    The artifact and evidence flow is:

    baseline induction SessionRecords
  ── evaluator projection ──► two EvidenceDraft failure records
  ── PullAccess analyzer ──► structured patterns and procedures
  ── builder SessionRequest ──► SkillSet(skills/sealqa.md)
  ── two equal held-out pairs ──► two external comparisons
  ── retain ──► LabResult

    There is no mutable skill before phase 3. The analyzer proposes an explanation, the builder proposes Markdown, schema checks lift that Markdown into the versioned artifact, and only fresh held-out evaluations measure it. If analysis or building fails, the lab retains the typed failure and does not spend the held-out sessions.

    The eight sessions¶

    # Session Purpose
    1 Induction episode 1 Run the unchanged baseline on frozen row 5.
    2 Induction episode 2 Run the unchanged baseline on frozen row 6.
    3 Failure analyzer Pull both recorded failure records and propose patterns/procedures.
    4 Skill builder Convert the analysis into one Markdown skill with checks.
    5 Held-out 1 baseline Run unchanged instructions on frozen row 7.
    6 Held-out 1 skill Run identical instructions plus the skill on row 7.
    7 Held-out 2 baseline Run unchanged instructions on frozen row 8.
    8 Held-out 2 skill Run identical instructions plus the skill on row 8.

    There is no skill evaluation on induction rows and no skill construction from held-out rows. That isolation prevents the builder from simply encoding the answers on which the skill is judged.

    What an induction failure contains¶

    Each completed induction episode is graded locally. The experience record contains:

    {
  "case_id": "longseal-004",
  "prediction": "the agent's answer, if any",
  "exact": 0.0,
  "failure_kind": null
}

    If the provider or adapter fails, exact is absent and failure_kind names the typed outcome. The record deliberately omits:

    • the evaluator's expected answer;
    • source or gold URLs;
    • the gold-document label;
    • held-out row contents.

    This makes the failure complete as an observation of what the agent did without turning evaluator secrets into proposer-visible experience.

    Shipped experience-pull seam¶

    The analyzer is not handed a manually concatenated failure report. The two failure records are committed as seed evaluation evidence in an ordinary inner run, and the analyzer receives bounded meta.PullAccess:

    meta.PullAccess(
    max_operations=20,
    max_results=20,
    max_records=100,
    max_chars=32_000,
)

    A user-owned SDK custom tool can search and open those strictly prior records. The proposal must declare which experience it derived from. Pull usage is retained separately from provider token/wall usage.

    That distinction yields two different null results:

    skill did not help, analyzer used experience
skill did not help, analyzer never read the offered experience

    The second says nothing about whether failure-driven induction helps; it says the configured agent did not exercise the mechanism.

    Analyzer and skill contracts¶

    The analyzer returns:

    {
  "failure_patterns": ["General pattern observed across failures"],
  "procedures": ["Reusable action an agent should take"]
}

    The separate builder sees this analysis—not the held-out cases—and returns:

    {
  "skill_markdown": "# Skill title\n\nProcedure...\n\n## Verification\n- Check..."
}

    The emitted meta.SkillSet contains one path:

    skills/sealqa.md

    Keeping it as Markdown makes the learned procedure directly inspectable. The builder instruction requires explicit verification checks so the skill is more than generic advice such as “be careful.”

    Held-out comparison¶

    For each held-out row, two fresh sessions receive the same public question, documents, model, answer schema, turn/timeout/wall bounds, and exact grader. Only the instruction block differs:

    baseline arm
  base solver instructions

skill arm
  base solver instructions
  + rendered skills/sealqa.md

    Each pair is classified independently:

    Result Meaning
    improvement Skill exact score is higher.
    tie Both valid arms have the same score.
    regression Skill exact score is lower.
    unrankable_typed_failure At least one arm has no metric.

    The report retains both results. It does not average a provider failure into a low score or hide a regression behind the other row's improvement.

    Minimal runnable mechanism¶

    from sealqa_labs import UserSdkSessionRunner
from sealqa_labs.evoskill import run

result = run(UserSdkSessionRunner(agent_factory=build_agent))

print("analysis:", result.artifacts.get("analysis"))
print("skill set:", result.artifacts.get("skill_set"))
print("experience usage:", result.artifacts.get("experience_usage"))
print("held-out comparisons:", result.artifacts.get("held_out_comparisons"))
print("measurements:", result.measurements)
print("usage:", result.usage)
    Illustrative shape — live run, nothing captured
    analysis: <failure patterns and procedures>
skill set: <one inspectable Markdown skill>
experience usage: <operations, records, characters, and unused evidence>
held-out comparisons: <two improvement, tie, regression, or failure labels>
measurements: <induction and held-out measurements>
usage: <aggregated provider usage>

    Run it with:

    META_EVOLVE_LIVE_SDK=1 uv run python your_sealqa_driver.py evoskill

    If analysis or building fails, held-out sessions are skipped: there is no valid skill artifact to compare. Eight is the maximum complete path.

    How to interpret the result¶

    Read these facts separately:

    1. Were the induction episodes valid wrong answers or typed failures?
    2. How many experience operations, records, and characters did the analyzer use?
    3. Are the reported failure patterns supported by both episodes?
    4. Does the Markdown skill contain concrete procedures and verification checks?
    5. What happened on each held-out pair—improvement, tie, regression, or failure?
    6. Did skill augmentation change provider usage as well as correctness?

    Two held-out examples demonstrate the comparison mechanism; they do not support a general claim that the skill transfers across SealQA or other task families.

    Isolation and validity checklist¶

    • Rows 5–6 appear only in induction and failure evidence.
    • Rows 7–8 appear only in the four held-out sessions.
    • Failure evidence omits reference answers, URLs, and split labels.
    • Analyzer and builder are separate provider sessions.
    • Pull counters show whether offered experience was actually used.
    • Baseline and skill arms otherwise share compatible declarations.
    • Ties, regressions, failures, and unused experience remain visible.

    Change and predict¶

    Remove the requirement for verification checks from the skill-builder instruction. Before running, predict:

    1. whether the skill becomes shorter but less actionable;
    2. whether analyzer pull usage should change;
    3. which held-out arm is most likely to tie or regress;
    4. what evidence would distinguish a bad skill from unused experience.
