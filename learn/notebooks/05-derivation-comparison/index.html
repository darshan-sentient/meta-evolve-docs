    Trace derivation and compare memory strategies¶

    Status: Shipped.

    Seeing a record and using it are different facts. This chapter shows how a proposal makes a causal-use claim, how the coordinator validates it, and how runs with different memory declarations can still be compared honestly.

    Open the canonical executed notebook only for executable inspection.

    What it teaches¶

    ProposalResult.derived_from is not a free-form citation. It is an ordered set of typed references to prior records the proposer was authorized to observe.

    available history ── push/pull policy ──► observation ledger
                                              │
proposal declares derived_from ───────────────┘
                                              │ validate
                                              ▼
                                     committed causal edges

    The edge survives regardless of whether the proposed artifact later scores, fails evaluation, or loses search selection.

    Follow the constructed run¶

    All four variants spend the same task usage:

    for name, (result, _) in results.items():
    outcomes = tuple(
        trial.failure.kind
        if trial.failure is not None
        else trial.metrics["score"]
        for trial in result.trials()
    )
    print(
        f"{name:<10}",
        f"outcomes={outcomes}",
        f"task_usage={result.summary().usage}",
    )
    Output
    no-memory  outcomes=(0, 'evaluator_failure', 'evaluator_failure', 'evaluator_failure') task_usage=Usage(evaluations=4, trials=3, tokens=0, spend_micros=0, wall_seconds=0.0)
push-only  outcomes=(0, 'evaluator_failure', 'evaluator_failure', 10) task_usage=Usage(evaluations=4, trials=3, tokens=0, spend_micros=0, wall_seconds=0.0)
pull-only  outcomes=(0, 'evaluator_failure', 'evaluator_failure', 10) task_usage=Usage(evaluations=4, trials=3, tokens=0, spend_micros=0, wall_seconds=0.0)
combined   outcomes=(0, 'evaluator_failure', 'evaluator_failure', 10) task_usage=Usage(evaluations=4, trials=3, tokens=0, spend_micros=0, wall_seconds=0.0)

    The no-memory arm produces three evaluator failures after its seed. Push, pull, and combined arms observe the first two failures and produce 10 on the third proposal.

    This separates three stages:

    1. observation may influence proposal;
    2. the proposal commits an artifact and causal claim;
    3. independent evaluation decides whether that artifact is rankable.

    Exact committed edges¶

    Read each committed proposal's derivation in logical-step order:

    for name in ("push-only", "pull-only", "combined"):
    result, _ = results[name]
    projection = result._projection()
    print(name)
    for submitted in projection.proposals:
        trial = projection.completed_trial(submitted.proposal.trial_id).trial
        kinds = tuple(ref.kind for ref in submitted.proposal.derived_from)
        print(f"  step={trial.logical_step} derived_from={kinds}")
    Output
    push-only
  step=1 derived_from=()
  step=2 derived_from=('evaluation',)
  step=3 derived_from=('evaluation', 'evaluation')
pull-only
  step=1 derived_from=()
  step=2 derived_from=('evaluation',)
  step=3 derived_from=('evaluation', 'evaluation', 'trial', 'trial')
combined
  step=1 derived_from=()
  step=2 derived_from=('evaluation',)
  step=3 derived_from=('evaluation', 'evaluation', 'trial', 'trial')

    Why trial references matter: an evaluation says how an artifact was measured; a trial occurrence carries the causal attempt in which it appeared. The artifacts could even have equal content while their trial identities differ.

    A failed evaluation does not erase derivation¶

    Suppose step 2 legitimately uses the step-1 failure, proposes candidate 2, and then candidate 2 also fails evaluation. The causal statement remains true: the earlier failure influenced the proposal. Removing the edge would confuse “the idea did not work” with “the idea was never used.”

    Typed outcome and causal lineage are orthogonal:

    Proposal valid? Evaluation valid? Artifact committed? Derivation kept? Rankable?
    Yes Yes Yes Yes Yes
    Yes Typed evaluator failure Yes Yes No
    Typed proposer failure Not run No Valid refs may be recorded on failure evidence No
    Invalid derivation Not run No No No

    Validation rules¶

    A derivation declaration must be:

    • made of typed ExperienceRef values;
    • unique;
    • strictly prior to the proposal;
    • authorized by its push/pull observation ledger;
    • in the same order as first observation.

    The coordinator, not the proposer, enforces those rules. An unauthorized edge becomes PolicyViolation and no candidate is committed.

    Failure precedence is deliberate:

    resource exhaustion
  outranks invalid derivation
    outranks proposer-reported failure

    This reports the strongest coordinator-owned fact. A proposer cannot hide an invalid causal claim by also returning a convenient failure.

    Replay preserves the graph¶

    Committed proposals contain the derivation references. Replaying the retained event stream rebuilds identical graph edges:

    result, storage = results["combined"]
events = storage.events.read(result.id)
left = replay_experience_graph(result.id, events)
right = replay_experience_graph(result.id, tuple(events))
query = ExperienceQuery(task_id=left.task_id, run_id=result.id)

left_edges = tuple(node.derived_from for node in left.state_at(query).nodes)
right_edges = tuple(node.derived_from for node in right.state_at(query).nodes)
print("replayed derivation equal:", left_edges == right_edges)
print("edge sizes:", tuple(len(edge) for edge in left_edges))
    Output
    replayed derivation equal: True
edge sizes: (0, 0, 1, 4)

    Replay does not call the context selector, reader, filtering logic, or renderer. It validates the facts that were actually committed at that logical time.

    Empty derivation is omitted from canonical serialization for compatibility with older proposal bytes. Non-empty derivation is encoded and round-trips exactly. An explicitly encoded empty default is rejected as non-canonical so one logical value has one byte representation.

    projection = result._projection()
bootstrap = projection.bootstrap.proposal
derived = projection.proposals[-1].proposal
bootstrap_bytes = serialization.dumps(bootstrap)
derived_bytes = serialization.dumps(derived)

print("empty derivation omitted:", "derived_from" not in bootstrap_bytes)
print("non-empty derivation encoded:", "derived_from" in derived_bytes)
print("round trip exact:", serialization.loads(derived_bytes) == derived)
    Output
    empty derivation omitted: True
non-empty derivation encoded: True
round trip exact: True

    Fair comparison when memory differs¶

    The experiment is specifically asking whether memory access changes outcomes, so context and pull declarations are allowed to differ. Compatibility still requires equal:

    • evaluator and proposer declarations;
    • objectives and artifact contract;
    • task and run budgets;
    • initial artifact digest;
    • other behavior-affecting task conditions.

    The comparison reports the intended differences, including a true self-tie:

    baseline = results["no-memory"][0]
for name, (other, _) in results.items():
    comparison = baseline.compare(other)
    winner = comparison.winner.primary_score if comparison.winner else "tie"
    print(
        f"no-memory vs {name:<10}",
        f"winner={winner}",
        f"same_seed={comparison.same_random_seed}",
        f"same_context={comparison.same_context_declaration}",
        f"same_pull={comparison.same_experience_declaration}",
    )
    Output
    no-memory vs no-memory  winner=tie same_seed=True same_context=True same_pull=True
no-memory vs push-only  winner=10 same_seed=True same_context=False same_pull=True
no-memory vs pull-only  winner=10 same_seed=True same_context=True same_pull=False
no-memory vs combined   winner=10 same_seed=True same_context=False same_pull=False

    That is more informative than either rejecting all memory experiments or pretending their declarations are equal.

    What a winner means here¶

    The primary score is 10 versus 0, so the memory-aware run wins inside this task. The comparison does not say:

    • which particular retrieved record caused the numerical gain beyond the proposer's declared claim;
    • that memory improves other tasks;
    • that larger context is cost-effective for a model;
    • that the winning artifact should be deployed.

    Those require additional tasks, ablations, cost objectives, and external promotion policy.

    What to notice¶

    • Derivation belongs to proposal causality, not evaluation success.
    • Every edge must come from an authorized ordered observation ledger.
    • Replay rebuilds edges without rerunning retrieval.
    • Comparison may intentionally vary memory strategy while holding the task contract fixed.
    • Compatibility flags make those independent-variable differences visible.
    • Promotion remains outside both search and comparison.

    Interpretation questions¶

    1. Why retain derivation for a candidate that fails evaluation?
    2. Can a proposer cite a record returned after the proposal completed?
    3. Why does comparison permit different memory declarations here?
    4. Does derived_from prove the referenced information truly caused a model's internal reasoning?
    Answers 1. The reference can still have caused the attempted candidate; outcome and causality are separate facts. 2. No. It was not in the strictly-prior committed observation ledger. 3. Memory strategy is the experiment's intended independent variable; the comparison reports rather than conceals that difference. 4. No. It is the proposer's explicit, validated usage claim. Stronger causal evidence requires controlled ablations or interventions.

    Change and predict¶

    Modify the proposer to cite the same evaluation reference twice.

    Predict: ProposalResult rejects duplicate derivation before a candidate can be treated as successful. No artifact from that proposal becomes rankable, and the invalid edge never enters the replayed graph.
