    Positioning and documentation update plan¶

    Prepared September 16, 2026. The first documentation update is recorded below; incoming methods retain their individual availability and acceptance gates.

    This plan turns the methods-library positioning discussion into documentation work. It anticipates incoming method implementations without changing their availability, public APIs, or acceptance gates. The programming model, architecture, milestones, and implementation plan retain their existing ownership. The current runtime boundary remains M11; this plan creates no runtime scope.

    Positioning decision¶

    Present Meta-Evolve as a Python framework and growing library of methods for evolution and meta-evolution. Lead with what someone can build and reuse:

    Apply, compose, and evolve improvement methods.

    Meta-Evolve is a Python framework for evolution and meta-evolution. Build methods for optimization, research, and scientific discovery by defining what can change, how revisions are proposed, and how outcomes are evaluated. Apply an implemented method, compose your own, or evolve a method through the results it produces.

    Use the same core wording in the README, homepage, and site description. Keep the canonical project definition intact. Here, a method means a concrete algorithm or procedure assembled with existing APIs; it introduces no new public Method class or universal method-switching parameter.

    The primary entry is a developer applying a method to an existing problem. The next two paths serve developers and researchers composing methods and studying meta-evolution. Infrastructure benefits support these paths.

    Promise User payoff Documentation proof
    Many methods, one programming model Reuse knowledge, evaluators, and compatible components across methods Method catalog and two substantial implementations mapped to the same component model
    Artifacts with their own structure and edits Represent the actual thing being improved Text, source, skills, harness, and custom-domain examples
    Methods can be composed Build a useful variant without rebuilding the execution infrastructure One executable composition showing the reused and newly authored pieces
    The improvement procedure can evolve Produce a reusable recipe or policy for a task family An outer experiment, its inner results, and a fresh final comparison

    Experience controls, user-owned SDKs, retained evidence, typed failures, and configured durability explain why the framework is useful as methods become more complex. They follow the core story instead of becoming the opening pitch.

    Diagnosis before this update¶

    • README and homepage open with a handwritten parser repair. It teaches the callable API well, but does not introduce the intended breadth of methods.
    • Method discovery sits under Examples → Research, alongside unimplemented mappings and adjacent references. A reader cannot immediately identify the library they can use.
    • Composition and meta-evolution are mostly advanced destinations. Their practical payoff appears after a reader has already chosen a tool.
    • The comparison now has accurate qualifications, but its main story is controlling experiments. It should also explain applying, composing, and evolving methods, supported by concrete examples.

    Retain the existing self-contained tutorials, canonical source snippets, downloads, historical URLs, and evidence records while changing the emphasis.

    Reader journeys and information architecture¶

    Make three paths visible in the first screen of the homepage and README:

    1. Use a method: choose a goal, see the implemented scope and requirements, run the method, inspect its result, and replace the task-specific inputs.
    2. Compose a method: identify the artifact, proposal logic, evaluation, search or stage schedule, and experience; reuse compatible pieces and run a concrete variant.
    3. Evolve a method: define the editable procedure, measure it through bounded inner tasks, inspect supporting results, and perform a fresh final comparison.

    Proposed top-level navigation: Start here · Methods · Guides · Examples · Concepts · Reference · Development. The logo continues to open the homepage.

    Promote research/index.md to the Methods navigation destination without changing its URL. Present runnable entries first, grouped by reader goal: prompts; skills and context; agents and harnesses; data generation; research procedures and search; code and systems; scientific discovery. Retain research directions and adjacent references in a clearly identified later section at the same owner.

    Examples remains the application and execution-mode chooser. Both indexes link to the same canonical walkthroughs. Search presets remain building blocks in Guides and Reference; their presence does not count as complete paper implementations in the method library.

    Homepage and README content order¶

    1. Positioning, short explanation, and the three journey links.
    2. A small set of named methods connected to practical outcomes. Initial editorial candidates: AutoResearch, AutoData, skill/playbook evolution, harness evolution, code/systems optimization, and scientific discovery mappings with their declared status. Additional methods join as their own implementation gates pass.
    3. One diagram: a method improves an artifact; an outer evaluation measures an editable method through the artifacts or outcomes it produces. Show which evaluator and task inputs remain fixed.
    4. Four short value statements corresponding to the positioning promises.
    5. Complete runnable quickstart with installation and all definitions.
    6. Links to adaptation, inspection, SDK integration, and deeper documentation.

    Preserve the parser's low-friction teaching role. It is not the flagship proof of algorithm quality. Do not open with greedy-versus-population results or a large table of internal protocols. Documentation navigation needs no new runtime API.

    Method-page contract¶

    Each implemented method's canonical walkthrough should answer, in order:

    1. What problem does it solve? Name the intended user, artifact, and output.
    2. What does this implementation do? State availability and exact algorithm scope, with a compact flow diagram where stages or nesting matter.
    3. What do I need? Installation, dependencies, data, credentials, execution environment, and expected resource use where measured.
    4. How do I run it? One complete supported entry point, real source, and captured output or an explicitly identified illustrative output shape.
    5. What does the result mean? Show the selected artifact or recipe, measurements, and a relevant failure or negative outcome when available.
    6. How do I adapt or compose it? Identify the task-specific replacement points and show one concrete change using supported components.
    7. What was verified? Distinguish mechanism tests, live evidence, and reproduction claims; link upstream sources and detailed evidence.

    Keep setup and usable code together. Name whether the artifact is a generated item, the generator's recipe, an agent, or the procedure improving that agent. Explain multiple stages in their actual order. Include the independent final evaluation when the method provides one.

    Use only Shipped, Experimental/live-only, and Design—not shipped as status labels. Describe implementation completeness and evidence separately in plain sentences. A shipped mechanism fixture does not establish a complete implementation or reproduce a paper's results. Keep scope visible at the point of choice without repeating a long disclaimer in every paragraph.

    Three demonstrations that substantiate the positioning¶

    Demonstration Required reader-visible result Existing starting point
    Apply a method to a useful artifact A complete run, selected output, and an explicit adaptation to the user's task Skill/playbook, harness, or systems example; choose the clearest implementation ready for the release
    Compose a method Executable code showing which proposal, selection, feedback, or schedule component changed and what was reused Composition worksheet and transfer guide; bind to incoming methods once compatible implementations exist
    Evolve a procedure Baseline and selected recipe, inner outcomes, resource use, and fresh final evaluation AutoResearch and policy evolution

    AutoData additionally demonstrates a method with several stages: generation, restricted/informed solving, acceptance checks, rewriting, and reevaluation. Its current lab is Experimental/live-only, uses user-owned orchestration, and retains a LabResult, not a durable outer run. Its new page must follow the implementation that actually ships rather than assume these properties have changed.

    Composition examples must preserve the distinctive algorithmic choices of the methods they name. The current Specialists preset is not the complete GEPA algorithm. A recipe assembled from selected mechanisms should be described as that recipe. Reusing a task also does not automatically establish equal model cost or a fair performance comparison.

    Release sequence¶

    Change 1 — Positioning and discovery. Update the opening copy, journey links, navigation, comparison, and editorial conventions. Feature currently runnable scope accurately. Retain complete entrance code and historical routes. This change can ship before the incoming method implementations.

    Change 2 — Method library and authoring guidance. Reorganize the existing catalog, apply the method-page contract to representative available methods, and make the composition and meta-evolution routes visible. Use existing metadata and checks; do not create placeholder implementations or invent convenience imports. Incoming method PRs adopt the same page contract.

    Change 3 — Demonstrations with the method releases. Attach the three demonstrations to the actual ready implementations. Method owners supply source, setup, evidence, and their algorithm acceptance tests. Documentation work supplies the reader journey and composition explanation. Add further catalog entries and homepage selections incrementally; no all-method release is required.

    Each method's implementation PR updates its canonical page, catalog metadata, source/download/notebook links, evidence, and relevant navigation together. Its existing milestone or research issue owns acceptance; this plan adds no algorithm implementation mandate or promised release date.

    Verification and acceptance¶

    • A reader can explain the three journeys after reading the entrance overview.
    • A featured method's setup and supported run are reachable within two content links from the homepage, without searching through research proposals.
    • The reader can distinguish an artifact, an improvement method, and the evaluator; AutoData and AutoResearch make their candidate boundaries clear.
    • Every advertised implementation has a working entry point and explicit scope. Catalog, walkthrough, and homepage availability agree.
    • Claims about composition point to executed code showing actual reuse. There is no implied universal compatibility or automatic one-line swap.
    • Existing URLs and fragments retain their meaning. README and homepage quickstarts still execute independently with the installed package.
    • Competitor claims are checked against primary sources at publication time. OptimizeAnything's engine/custom-evaluator extension points are acknowledged; comparisons describe supplied capabilities and authoring work.
    • Performance claims link retained results and their setup, resource use, failures, and evaluation scope. Documentation proof does not require a positive score improvement on every demonstration.

    During implementation, extend the existing entrance, guide-navigation, documentation-route, research-catalog, and ownership checks to protect these reader outcomes. Reuse the relevant example and installed-package checks from the Docs workflow. Run the strict MkDocs build and inspect the rendered entrance, catalog, method page, and nested-loop diagram on desktop and mobile. Test meaningful routes and executable content; do not assert marketing adjectives or freeze the precise menu layout.

    Decisions fixed for the first implementation¶

    • Methods become a primary discovery destination at the existing catalog URL.
    • The entrance message is applying, composing, and evolving methods.
    • Structured artifacts and reusable procedures are explicit product benefits.
    • The parser remains a complete quickstart below the product overview.
    • Optimization, research, and scientific discovery define the broad scope. AutoResearch, AutoData, agent/skill methods, and systems work are examples; availability and completeness follow their owning implementations.
    • The implementation-ready release shortlist is resolved from the methods actually landing; it changes featured entries, not the documentation model.

    Implementation record¶

    The first update implements the shared entrance message, three reader journeys, Methods navigation, catalog reorganization, comparison, composition guide, meta-evolution diagram, and editorial contract. It keeps the complete parser quickstart and historical routes. Scientific discovery is explicit in the application scope; method implementations and catalog statuses are unchanged.

    Verification on September 16, 2026: the strict MkDocs build, 106 focused documentation checks, and 14 notebook checks against a fresh installation of the generated source ZIP passed. The documented context-evolution command ran both skill and playbook compositions with the retained output. Notebook and confined-process checks required execution outside the agent sandbox. Desktop and mobile visual inspection remains unverified: no browser surface was available, and the local machine was locked.

    Incoming method releases still supply their implementation-specific setup, adaptation, evidence, and acceptance tests. They should follow the page contract above and extend the demonstrations as their own gates pass.
