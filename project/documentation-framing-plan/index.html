    Documentation framing and refinement plan¶

    Status: Design—not shipped.

    Prepared September 17, 2026, against repository revision acd572ab2104. Implementation records cover #306/#307, the #308 method explanations, the #309 research context, and #310's contributor map and integration checks.

    Outcome and scope¶

    Give readers one connected explanation: improve an artifact, make a declared part of its improvement procedure the next candidate, and study whether that procedure becomes better at producing further improvements. Explain the evaluation and authority boundaries at each step.

    The September 16 positioning update introduced the use, compose, and evolve routes; this refinement connects them to the loop and examples.

    The programming model, architecture, milestones, and implementation plan keep their canonical ownership. The runtime build boundary remains M11. This work changes explanations, discovery, and contributor orientation; any new runtime mechanism or research experiment needs its own acceptance gate.

    Agreed homepage and README opening:

    Improve solutions. Improve the methods that produce them.

    Meta-Evolve is a Python framework for applying, composing, and evolving improvement methods. Define what can change, propose revisions, and measure the results. Then make a declared part of the improvement procedure the candidate and evaluate the outcomes it produces.

    Follow with the existing three entry links, one compact diagram, and a sentence explaining that evaluation, budgets, permissions, and promotion remain under external control. Keep the canonical library definition available below this introduction. Treat “improve” as the purpose of a search, not a guaranteed result.

    Conceptual model, notation, and diagrams¶

    Use the parser to teach artifact evolution, the policy fixture to expose the inner/outer boundary, and AutoResearch to show why evolving a reusable procedure is useful. These roles are relative to an experiment, not intrinsic artifact types.

    View Candidate and question Evidence needed
    Evolution An artifact: which revisions work under this task's evaluation? Candidate measurements and outcomes under the declared controls.
    Meta-evolution A procedure artifact: which permitted procedure produces better task outcomes? Bounded executions, their costs and failures, and a fresh final comparison where provided.
    Recursive improvement A changed procedure helps generate subsequent changes to the improvement procedure. Traceable reuse across generations and evidence about subsequent improvement ability under comparable controls. Nesting alone is insufficient.

    The symbols are our teaching shorthand, inspired by the distinction in the discussion; they are not presented as notation copied from Schmidhuber. Define them once in the improvement loop, with the procedure parameter added in meta-evolution.

    Symbol Meaning
    A The candidate artifact; A₀ is the seed.
    I A concrete improvement procedure, possibly composed from several runs or stages. No new public Method type is implied.
    E The independent evaluation setup; use “experience” or H for authorized prior observations, never overload E.
    B The externally supplied work allowance.
    R Retained execution results. A single experiment returns a Run; a composed method may retain several runs or its documented result type.
    θ, Iθ A declared procedure artifact and the procedure obtained by interpreting it under fixed controls.

    Start with a result-producing execution rather than an equation promising a better artifact at every step. The following is conceptual notation, not Python:

    R = Execute(I, A₀; E, B)
A_selected = Selected(R)             when an eligible result exists

R_j(θ) = bounded execution of Iθ on fixed inner task j
E_outer(θ) = evaluator-owned aggregation of the inner results

    The same execution schema applies outside: the seed becomes θ₀ and the evaluator becomes E_outer. A recursive experiment additionally records how a selected procedure is used to generate subsequent procedure candidates.

    The selected artifact can be the seed. A search may branch, retain weaker stepping stones, fail, or exhaust its allowance. Aggregation follows the method's actual outcome contract; an invalid or failed evaluation is not a low numerical score. Authorized experience can affect proposal and search decisions without exposing all recorded history or held-out data.

    Keep formulas optional and below the concrete explanation. Use text notation and existing diagram tooling in the first pass: the current site has no math renderer. A future typesetting change must preserve offline reading and README legibility. Keep the quickstart free of a notation prerequisite.

    Keep the shared docs/_includes/evolution-levels.md diagram compact: proposal, evaluation, and search, with labels for the candidate and fixed controls. The meta view encloses bounded inner work inside the outer evaluator. The detailed loop page shows seed evaluation, branching, rejection, and optional feedback. Use text as well as color; explain selection without implying deployment or universal monotonic gains.

    Research context and claims¶

    The blog motivates the discussion. Historical and algorithmic statements should link the primary work with a check date and the exact scope inspected.

    Source and proposed owner Supported use and required qualification
    1987 thesis, pp. 7–13; meta-evolution concept Introduce the historical connection to evolving program-modifying programs. The author's overview was checked September 17; verify the original pages before final historical wording. Do not infer why this repository was named or repeat priority claims.
    Self-modifying policies / SSA; survey context Explain empirical reward-rate evidence. The mutable policy can influence evaluation timing, but the text separately defines the acceptance algorithm; avoid a blanket claim that it controls its own judge.
    Gödel Machine; survey context Describe utility proofs conditional on the encoded assumptions and provability. A rewritable proof searcher does not mean an unjustified change to the criterion is accepted.
    OOPS bias-optimality; survey context Describe search efficiency relative to a bias and cost model. This is a different kind of guarantee from either empirical usefulness or a proof authorizing a self-rewrite.
    DGM, HGM; comparison and existing mappings Compare scope and measured mechanisms, including HGM's descendant productivity. Keep local mappings Design—not shipped; existing tree search does not establish a full HGM implementation.
    Red Queen Gödel Machine; comparison via existing research context Describe evaluation co-evolution under its stated controls; preserve its current inventory role as an A8 precedent, with critic governance owned by #251. No shipped integration is implied.
    Self-Improvements in Modern Agentic Systems; optional related reading Abstract checked September 17. Read the relevant full section before adopting any taxonomy or detailed claim.

    The SSA definition, OOPS definition, Gödel Machine abstract, and contemporary paper abstracts were checked September 17, 2026. Recheck detailed comparisons against the corresponding full method sections when drafting them.

    Keep the existing survey's attributed autonomy taxonomy separate from these conceptual views. Discuss empirical evidence, conditional proof, and search efficiency as different justifications, not “three survival tests” implemented by Meta-Evolve. Its examples demonstrate evaluated mechanisms; a held-out comparison does not establish acceleration of learning or a proof of utility.

    In the comparison page, describe what Meta-Evolve supplies and what authors must supply. Do not assume all other systems lack independent evaluation. Explain that authority is a contract enforced by the configured execution boundary; an ordinary in-process Python callable is not a security sandbox. Feedback controls likewise govern what is disclosed, rather than oppose the use of experience for learning.

    Implementation sequence and acceptance¶

    Use five reviewable changes in dependency order. None changes capability status. Track them as native subissues of documentation parent #274. The entrance, method, and research issues depend on the conceptual foundation; final integration depends on all three. Source research can start earlier.

    Change Deliverables Acceptance
    1. Establish the explanation — #306 Loop, meta-evolution, shared diagram, terminology, authority and experience clarifications The parser and policy examples can be explained with the same roles; selection, promotion, evidence, and disclosure remain distinct.
    2. Connect the entrance — #307 Homepage, README, site metadata, concept ordering, start-here transitions All three journeys work; users reach complete executable code without reading theory; existing routes and downloads remain valid.
    3. Teach through methods — #308 Policy and AutoResearch annotated traces; consistent introductions for the representative methods and composition/reference links Every statement matches current source, controls, outcomes, and catalog scope; differences between method algorithms remain visible.
    4. Place the research accurately — #309 Short history, comparison entry, survey context, source dates and claim qualifications Each external claim has a supporting primary source; no fixture, nested run, or unshipped mapping is presented as demonstrated RSI.
    5. Align contributor guidance and verify — #310 Code-tour map, example index, editorial conventions, final link and wording pass Canonical ownership is preserved, the documentation checks pass, and the reader walkthrough below succeeds.

    At each change, inspect the rendered affected pages and run focused checks. At integration, run the strict MkDocs build and the documentation test selection in .github/workflows/docs.yml, including historical routes and anchors, research metadata, snippet ownership, and download checks. Exercise the affected downloads in the workflow's fresh-install environment; use recorded evidence and injected providers rather than requiring new paid live calls.

    Add or adjust tests only for durable requirements: reachable reading paths, correct source extraction, preserved status and authority, and usable artifacts. Avoid tests that freeze optional wording, equation typography, or menu order. Do not regenerate historical notebooks or relax compatibility fixtures merely to make a changed page pass. Keep hand-written files normally below 300 lines.

    Run a reader walkthrough and record observations without treating it as a scientific result. A new reader should be able to find runnable code from the homepage; name the candidate, proposer, evaluator, and search in that example; explain what changes when the policy becomes the candidate; find the controls and fresh comparison; and identify what the fixture cannot establish about RSI. A contributor should locate the corresponding behavior and invariant tests from the code tour. Fix failed tasks before calling the refinement complete.
