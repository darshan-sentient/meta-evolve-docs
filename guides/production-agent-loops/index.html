    Production agent loops¶

    Status: Experimental/live-only. The Meta-Evolve composition below uses shipped local primitives. No production-scale tokenizer run or provider capture is retained in this repository.

    Liquid AI's tokenizer-trainer experiment is a useful picture of an evaluated source loop. Two coding agents started from a short outcome-and-constraints specification. Their early implementations passed toy tests, then failed against production data until repeated diagnosis, source changes, and external verification produced a production-grade result. The external harness loaded output with tiktoken and Hugging Face tokenizers, then checked round trips and ID-level agreement. The released toktoktok repository keeps the original AGENTS.md specification.

    Meta-Evolve can own the control plane for that shape. It does not provide the coding model, corpus, production machine, or security boundary.

    Run the miniature first¶

    The credential-free agent_test_repair example exercises the same authority boundary at local scale:

    uv run python examples/agents/agent_test_repair/main.py

    Its source candidate is an immutable SourceTree. A proposer repairs a private workspace, while an evaluator-owned grader outside the tree decides whether the result passes. Replace the deterministic fixture with a user-owned SDK wrapper to put a live coding agent in the same seat.

    Scale the same loop¶

    fixed specification + seed SourceTree
                  │
                  ▼
       user-owned coding-agent proposer
                  │
                  ▼
          immutable source candidate
                  │
                  ▼
        evaluator-owned real-data harness
        ├─ build and compatibility checks
        ├─ production-corpus execution
        ├─ peak memory and throughput
        └─ third-party output equivalence
                  │
                  ▼
         metrics + diagnostic evidence
                  │
                  └──────── next bounded trial

    The experiment declaration stays small because the provider and production runner remain user-owned adapters:

    import meta_evolve as meta

SPECIFICATION = """Build a memory-bounded, multithreaded BPE trainer ..."""


def tokenizer_experiment(build_agent, evaluator, seed):
    budget = meta.Budget(
        evaluations=13,
        trials=12,
        tokens=8_000_000,
        wall_seconds=7 * 24 * 60 * 60,
    )
    task = meta.Task(
        evaluator=evaluator,
        artifact=meta.SourceTree,
        objectives=(meta.Maximize("production_score", satisfy=1.0),),
        budget=budget,
        environment={
            "corpus_digest": "sha256:...",
            "harness_version": "tokenizer-v1",
            "hardware_profile": "epyc-9755-2tb-v1",
        },
    )
    return meta.Experiment(
        task=task,
        seed=seed,
        proposer=build_agent(SPECIFICATION),
        search=meta.Greedy(max_trials=12),
        context=meta.AncestorsOnly(max_records=20, max_chars=32_000),
        experience=meta.PullAccess(
            max_operations=40,
            max_results=40,
            max_records=200,
            max_chars=256_000,
        ),
        random_seed=0,
    )

    build_agent owns SDK authentication, tools, session behavior, and provider telemetry. evaluator owns the production runner and returns an EvaluationResult. The corpus digest, harness version, and hardware profile are part of task identity rather than ambient assumptions.

    For a live local adapter, retain committed history without promising cold resume:

    with meta.Storage.durable("runs/tokenizer") as storage:
    run = meta.run(
        tokenizer_experiment(build_agent, evaluator, seed),
        storage=storage,
        mode="local",
    )

    Use durable-local only after every component has a registered reconstruction path and external calls are honestly retry-safe. A paid call or multi-day evaluation repeated after a crash is real work, even when its first result was never committed.

    Keep reality outside candidate authority¶

    Concern Owner
    Rust source Candidate artifact
    Outcome specification Experiment / proposer declaration
    Production corpus Evaluator environment
    Compatibility harness Evaluator
    Model tools and permissions User-owned proposer wrapper
    Trial and resource ceilings Task and run budgets
    Which candidate receives work Search policy
    Whether the result ships User or governance layer

    Do not place the hidden harness or mutable production data in the candidate SourceTree. The proposer may receive bounded diagnostics and read-only data access, but it must not be able to edit the judge. The shipped development subprocess is not a security sandbox; use a container, VM, batch worker, or other conforming sandbox provider for a production isolation claim.

    Give search a useful signal¶

    A final pass/fail check is necessary but weak feedback. A production evaluator can retain separate metrics and evidence while exposing one staged primary score:

    Score Observable boundary crossed
    0.10 release build succeeds
    0.25 toy vocabulary trains
    0.40 output loads in both third-party libraries
    0.60 token IDs agree on adversarial text
    0.80 production shard stays within its memory ceiling
    1.00 full production run completes within its declared limits

    Candidate defects such as a compiler error or incompatible vocabulary are rankable observations. An unavailable corpus, dead worker, or broken harness is an unrankable typed failure. Never turn infrastructure reliability into a score about the source.

    AncestorsOnly supplies selected-lineage feedback. PullAccess lets the agent inspect bounded prior evaluations, exact source occurrences, and canonical source diffs when rejected attempts also matter. Declare the observations used by a proposal in derived_from; that makes “this edit responded to that OOM trace” an auditable causal statement.

    Greedy is a good first policy when the staged score reflects progress. If the experiment must continue from the latest source even through temporary regressions, use a small explicit SearchProgram rather than weakening the evaluator to manufacture monotonic scores.

    Compare agent tracks honestly¶

    Run each model as a separate experiment with the same seed, evaluator, corpus, hardware profile, context and experience grants, and resource limits. Only the proposer declaration should differ. Report both lineages, trials to success, tokens, wall time, failures, and stopping reasons.

    Generic Run.compare() deliberately requires the same proposer and seed, so it is not the verdict surface for a model-vs-model experiment. Build a dedicated report that names the model as the treatment. Predeclare an equal stopping rule instead of choosing which arm to stop after seeing intermediate results.

    This reproduces the experimental structure, not Liquid AI's historical result. That result also depends on private production data, particular late-2025 model builds, exact tool policies, hardware, and operator decisions. A public replication should begin with a public multilingual/code corpus and a modest machine, then scale only after the evaluator and authority boundary have been tested adversarially.
