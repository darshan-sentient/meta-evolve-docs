    First-run documentation: plan for #331¶

    Status: Design—not shipped.

    Prepared September 19, 2026 for #331, the documentation entrance to #330. The intended result is a shorter route from opening the homepage to running a complete experiment, followed by a clear route to model-generated revisions, feedback, and saved history. This page plans the change; it does not implement the entrance or authorize unselected runtime behavior.

    The implementation verification record now records the source checks, visual review, and remaining publication handoff.

    The programming model owns executable API contracts, the architecture owns semantics, the roadmap owns acceptance gates, and the implementation plan owns technical boundaries. The existing documentation maintenance rules govern source ownership, historical routes, and useful checks.

    Decisions¶

    1. Keep the complete credential-free parser example. Move it above the two concept sections and discovery table in both entrances; retain the opening “Improve solutions. Improve the methods that produce them.” framing.
    2. Lead online setup with a direct install from the published documentation ZIP. Keep the matching local ZIP route for archived/offline documentation. A package-index command waits for actual publication under #319.
    3. Immediately after the first result, link the existing complete live parser journey. Offer the routing-prompt journey as the alternative domain. Reuse #269's examples rather than create another tutorial.
    4. Separate ordinary construction and inspection from extension protocols in the generated reference while preserving existing URLs and fragment IDs.
    5. Add a separate author-UX gate to the roadmap. Runtime work stays in #332–#335; integrated usability work stays in #336; #337 is a later design decision about SDK support.

    Proposed entrance¶

    Keep the same order in README.md and docs/index.md, with normal Markdown in the README and shared includes in the site:

    Order Reader sees
    1 Name, existing positioning, one short explanation, and a direct first-run link.
    2 Python 3.12+ requirement and one online install cell; nearby local-ZIP fallback.
    3 Complete existing proposer, evaluator, and run cells, in that order.
    4 Expected output, what the score measures, and the zero-proposal exercise.
    5 “Use your model next”: the complete live parser journey with feedback and saved history; routing prompt as an alternative.
    6 Adapt the example, then the artifact/method diagrams, discovery table, and use/compose/evolve routes.

    Do not make the first example look shorter by omitting definitions or adding helper imports. Reuse examples/learn/parser_quickstart.py unchanged unless a specific correctness issue appears. Preserve the existing explanation that its proposal is handwritten and its scores come from six actual Python checks. Keep setup visible and each displayed Python cell below 40 lines.

    The live continuation should explain its value in one sentence: a model proposes revisions from evaluator feedback, and the example saves a history that can be inspected later. Link its prerequisites and dry run; do not imply it needs no credentials, guarantees an improvement, or has retained model-performance evidence. The small SDK guide remains useful for connecting a callable, but is not the only next link.

    Update the shared setup and README's marked copy together. Remove the current unqualified “skip it if you already installed this package” instruction: equal version labels do not prove matching source. Recommend a fresh environment for the first run and explain restarting an already-imported notebook kernel. Do not introduce a download resolver, packaging workflow, or installer library.

    Wording and reference boundaries¶

    Use these terms consistently in the touched entrance, feedback, and persistence prose without renaming public fields or constructors:

    Reader-facing term Exact existing API meaning
    Proposal attempts trials= and usage().trials count attempts after the seed; an attempt may fail.
    Evaluations usage().evaluations includes the seed evaluation; do not promise every proposal reaches evaluation.
    Recorded history result.trials() includes the seed and attempted revisions; its length is not the proposal allowance.
    Feedback Evaluator observations made available to the proposer by the declared context policy.
    Experience The broader existing record/access vocabulary, including explicitly configured pull access.

    The default example keeps history in memory. Say that saving across processes requires explicit storage, with a link to the persistence guide. A selected seed is a valid result; completion does not imply improvement.

    For the reference, start with a small construction/inspection orientation, then render the ordinary author entries before the exhaustive export inventory and extension detail. Keep the existing four export tiers and generated signatures; do not prune root exports or duplicate manually maintained signatures.

    Use per-entry mkdocstrings member selection to keep Greedy and BestOfN constructors readable. Render binding/cohort methods once in a later extension section on the same API page, retaining anchors such as meta_evolve.Greedy.bind and meta_evolve.BestOfN.next_cohort. Link the existing extension guide. Preserve useful limitations when moving detail; serial distributed execution must not start sounding concurrent.

    Move milestone chronology out of beginner-facing prose. Do not rewrite Python component docstrings merely to hide design notes: source changes can affect recorded component identity. Prefer reference placement/configuration in #331; any necessary source edit needs its own explicit identity-impact review and focused verification. Avoid a global rendering filter or new template framework.
