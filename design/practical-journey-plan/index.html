    Practical journey and newcomer handoff: plan for #336¶

    Status: Design—not shipped.

    This is the integration plan for #336, under #330. It prepares one complete practical journey and the existing independent-review handoff. It does not implement an API, publish a package, or certify a newcomer session.

    The source implementation now follows this plan; the verification record owns actual results and remaining independent reviews.

    The programming model, architecture, author UX gate, and implementation plan remain authoritative.

    Outcome and entry gate¶

    Keep the credential-free first run. Make the existing routing-prompt journey show one continuous story: define independent checks, authorize development feedback, try bounded revisions, inspect measurements and typed failures, capture a useful snapshot, save history, reopen in a fresh process, and adapt the evaluator. A completed, understood experiment is success even when the seed stays best.

    Use the accepted contracts from these dependencies:

    Dependency Contract #336 consumes
    #331 Short entrance, matching install instructions, existing newcomer packet
    #332 context.evidence.latest(kind), enabled/truncated state, RecentAncestors
    #333 Capture RunSummary inside storage lifetime; render it afterward
    #334 One objective and explicit context on the small callable path
    #335 with meta.open_run(...), explicit or only-run selection

    Planning and partial rehearsals may precede dependency acceptance. Before #336 acceptance, all five need their accepted source, canonical contracts, and focused verification on the chosen integration revision. Open issues and concurrent local implementations are not proof of a matching installed package. Record that revision, dependency evidence, and any remaining limitations before integration. This work does not add a blocker to #319 or select a new release version.

    Reuse the routing journey¶

    Use examples/learn/llm/prompt.py, prompt_cases.py, and openai_client.py as the canonical complete journey. Its independent Python grader, request journal, development/final separation, and provider-replacement tests already exercise the difficult boundaries. Keep the three-file download and existing commands.

    The short SDK notebook remains the low-request introduction. The full journey continues to use 40 development cases, at most three revisions, and 12 separate final cases: at most 163 development requests plus 12 final requests, without retries. A preview remains a preview; it does not measure model accuracy. Do not change datasets, request defaults, or claim live improvement as part of this integration. The parser remains an alternative example, with its existing coverage retained rather than a second overhaul.

    Keep the two authoring paths honest¶

    Use #334's improve(objective=..., context=...) in the existing credential-free feedback lesson and the own-evaluator adaptation exercise where those declarations are sufficient. Keep an explanatory link to the equivalent expanded declaration; reuse the lesson's callables and tests rather than add a second implementation.

    Both SDK examples record model/request configuration in Task.environment; the complete driver also accepts an execution budget. Keep their explicit Task → Experiment → run path. Replacing it with improve() would discard identity or budget declarations. Do not add environment, budget, search, registry, mode, or pull-access keywords to make this example fit the small path.

    Make feedback complete and attributable¶

    Today the full routing evaluator emits one routing-case per ticket, and the proposer groups records by maximum logical step. latest("routing-case") would return only one ticket. Introduce one lesson-owned routing-feedback evidence report per returned evaluation outcome, containing the evaluated prompt's SHA-256, completed checks, completion state, and typed failure kind if present. Keep existing per-request/per-case evidence for inspection and partial-work receipts. This small, bounded duplication avoids a new grouping API or loss of diagnostics.

    Emit the report last, including when an evaluation returns a known typed failure. An interrupted evaluation has partial observations and no score; it must not pretend to have evaluated the remaining tickets. An accounting-unknown escape retains its existing receipts instead of manufacturing a completed report.

    The proposer reads context.evidence.latest("routing-feedback") under RecentAncestors, with explicit record/rendering bounds. Reserve this label for the trusted evaluator; SDK response evidence uses its existing distinct label. Check the report's prompt digest against the supplied parent before using it. This checks the report's subject, not evaluation-occurrence identity: equal prompt bytes can occur more than once, and the accessor's exact ref remains the source occurrence. Do not claim the accessor authenticates a producer.

    • Required feedback with disabled context raises ContextDisabled before a rewrite request. An enabled selection with no report, or a mismatched report, produces an actionable CapabilityError before dispatch; no silent empty or stale-feedback fallback. Known failed seed evaluations still have their report so a repair attempt can proceed.
    • Surface the aggregate truncation flag. Continue when a usable report for the parent remains selected; the flag alone does not prove that report is partial. Record omission and rendered-text clipping are different possible causes.
    • A deliberate feedback-off comparison uses an explicit optional-feedback guard in the existing feedback exercise. Do not weaken the full driver's requirement.
    • Render the selected structured report into the request. max_chars bounds bundle text, not item.data or SDK request size; the fixed development suite bounds the report. Never query omitted history or use final checks to fill gaps.

    Keep the first integration's existing context allowances unless focused tests justify a smaller bound. Tests must establish parent feedback after several revisions and rejected siblings; do not infer that a preset guarantees it.

    Show results and preserve storage ownership¶

    Capture and display result.summary() while the store is open. Retain a small attempt/evidence view and selected-prompt export beside the summary: aggregate counts alone cannot explain a failed attempt. Render the captured summary again after closing storage, without reading a live Run or re-executing an evaluator.

    Replace the manual read-only-store/Run construction in --inspect with open_run(directory / "history", run_id=...). Preserve run-id.txt for explicit identity, plus the chosen directory. Demonstrate only-run selection in the existing persistence guide, without inventing chronological ordering of IDs. Catch only the expected no-run case for an interrupted first request; missing or corrupt stores and ambiguous selection retain their typed diagnostics.

    Final evaluation stays after development selection and outside search history. Its results and usage remain in final.json. requests.jsonl overlaps history; their totals must not be added. Reopening performs no SDK calls and grants no resume capability. In-memory SDK notebook output says history is not saved durably.

    Deterministic acceptance scenarios¶

    Extend existing fixtures; substitute the provider or HTTP transport, not the grader, coordinator, accounting, or storage. Synthetic scores are test evidence only. A single live run is not required to happen to exhibit a failure.

    Scenario Required observation
    Improvement, tie, regression, satisfied seed Correct parent retained; complete parent report used; stop reason and proposal/evaluation counts agree with history
    Seed remains best Completed experiment and useful summary; no promised positive delta
    Missing required metric or all evaluations fail Typed evaluation failures, no invented score/winner; inspectable summary and retained usage; no final check without selection
    Disabled required feedback ContextDisabled before rewrite dispatch; enabled/no-match is a distinct case
    Missing or stale selected report Clear configuration diagnostic before rewrite; no reach outside the selected bundle
    Record truncation and text-only truncation Test separately, including max_records=0 and max_chars=0; flag is truthful and intact structured reports remain usable
    Rejected or failed sibling, repeated parent text Latest authorized report remains correctly associated; a digest does not replace occurrence provenance
    Wrong completed answer versus unavailable output Wrong labels remain measured mistakes; empty/incomplete output keeps typed failure with no score
    Failed rewrite or partially failed evaluation Known usage/evidence retained; failed rewrite skips evaluation; partial evaluation produces no fabricated full-suite score
    Unknown spend or token accounting Unknown spend stays None; unknown required accounting escapes with receipts, committed prefix, and no hidden retry
    Snapshot and reopen Snapshot renders after close; fresh process uses only installed package and saved files; queries make zero SDK calls
    Empty/multiple-run stores and explicit selection Expected typed diagnostics, explicit ID works, no lexical-recency assumption or hidden fallback
    Final evaluation succeeds or fails No final case/result in development history or rewrite requests; final failure never reopens search; usage remains separate

    Newcomer and QA handoff¶

    Extend the existing packet, which already separates setup time, own-evaluator completion, and unprompted feedback problems. Keep participant prompts separate from observer answers. Observe an unaided adaptation first, then use controlled fault scenarios; a diagnostic task does not establish that a problem occurred spontaneously.

    1. Start at the homepage, install matching artifacts, and finish the first run.
    2. Build a bounded experiment for the participant's small problem using their own evaluator; inspect the result, including when no revision improves it.
    3. Observe whether they independently discover, enable, and consume useful feedback. After recording that outcome, ask them to diagnose disabled, missing, and truncated feedback in prepared credential-free scenarios.
    4. Ask them to explain a typed failed attempt, a low measured score, proposal versus evaluation counts, and unknown spend using the recorded result.
    5. Save, restart, reopen, and inspect without the original callbacks; explain the snapshot's lifetime and why saved local history is not resumable.

    Add only missing observation fields: first unprompted feedback consumption; diagnosis of each feedback state; count/failure interpretation; successful reopen; abandonment and reason; and baseline/after docs, package, task, and assistance conditions. Time the own-evaluator task from its prompt to a completed run and inspected result; record setup separately. Record independent, assisted, blocked, abandoned, and not-attempted outcomes rather than reporting only successful times.

    Bhasker and Salah agree session stopping rules and any timing/comparison thresholds before interpreting sessions. Preserve #275's requirement that three unfamiliar users complete the required journey without maintainer intervention after fixes. Report individual observations and retest exposure; three sessions do not estimate confusion prevalence. The same participant's learned retest is not a fresh baseline.

    Remaining SDK glue and difficulty¶

    Inventory repeated author work for #337 with exact source locations: request configuration, token validation, typed output handling, Resources conversion, unknown/billed/estimated spend, partial-request receipts, and request journaling. Compare the short notebook with openai_client.py and the full driver. Record what differs and why; shared spelling alone does not justify a library helper.

    Estimated difficulty is medium, approximately 3–5 engineering days once dependency contracts are stable, including example/docs changes and installed rehearsals. This excludes external review, release work, live experiments, and participant scheduling. The main risks are incomplete/stale feedback, loss of SDK identity/accounting while simplifying, source/download drift, and mistakenly counting automated checks as independent usability evidence. A defect requiring new runtime semantics returns to the owning dependency; #336 stays integration.
