    Agent SDK accounting support: study plan for #337¶

    Status: Design—not shipped.

    This plans #337, under #330. The outcome is an evidenced decision about reusable SDK accounting support. A maintained recipe, retaining the existing wrappers, or deferring a helper can satisfy the issue. A lightweight implementation and decision provides runnable recipes and focused offline comparisons. The requested practical scope closes the decision with experiment-local reuse and no public helper. The broader matrix below is retained as optional follow-up guidance; its full runtime acceptance is not claimed or required for this closure.

    The programming model, architecture, author UX gate, and implementation plan remain authoritative. The SDK boundary reference owns the existing failure and accounting rules. The study does not expand #313/#319's release scope.

    Question and starting point¶

    After #336, can a small reusable recipe remove repeated accounting work from Codex, Claude Code's Agent SDK, and Pi integrations without hiding decisions about agent execution, paid work, unavailable measurements, or valid output?

    Use #336's completed journey and glue inventory. It shipped in source through #338. Planning baseline, September 19, 2026: a6ac22e7aab7239dd4adf777d43995d07bbcf5b8. Unrelated local release and harness planning edits were present; this is not a clean installed-artifact claim. Pin the actual source revision and SDK dependencies again when running the study.

    Codex, Claude Agent SDK, and Pi are the three required study targets. The issue's minimum of two materially different integrations is a floor; this plan uses all three to test the requested agent workflows. The short notebook and full lesson both use OpenAI Responses and serve as a simple regression control. No new live capture or newcomer session is needed to start this study; those remain distinct evidence under #269–#271 and #275/#277.

    Scope and comparison cases¶

    Compare a bounded agent invocation through each programmatic interface, including multiple model steps, tool execution, terminal events and partial failure. Use deterministic process/protocol/model fixtures and synthetic billing reports; keep outputs and tool observations fixed when comparing each wrapper to its candidate revision. Native event streams and asynchronous SDK consumption are in scope even though Meta-Evolve's outer callable path remains synchronous.

    Integration Starting implementation and meaningful difference
    Codex Use the official Python openai-codex SDK and its pinned CLI/app-server runtime. Start from CodexProvider in experiments/_live_support/providers.py and experiments/08_harness_evolution_live/codex_boundary.py. Trace thread/turn identity, tool activity, terminal status and the actual scope of reported usage.
    Claude Code via Claude Agent SDK Use Python claude-agent-sdk and its matching CLI. Start from AgentSdkProvider and experiment 11's accounting probes. Trace asynchronous assistant/tool/result messages, query versus session totals, terminal errors and auxiliary work.
    Pi Use Pi's programmatic agent interface. For this Python study, choose the documented JSON-over-stdio RPC path; consult the TypeScript SDK's session/event contract. Pin the Pi package/runtime and record the bridge's code and lifecycle cost. This is an agent integration, not a direct pi-ai model call or a claimed native Python SDK.

    Read the official Codex SDK, Claude Agent SDK, Claude accounting, Pi SDK and Pi RPC contracts. Sources checked September 19, 2026; pin package/runtime versions and recheck their field semantics before constructing fixtures.

    Two concrete traps justify this scope. Claude's ResultMessage.usage excludes nested work; model_usage covers more calls, and its streaming-input totals are cumulative. The documented coverage still excludes some helper calls. Its reported dollars are estimates, not billing statements. See the Python result contract. Pi's session statistics include reported tool and compaction work; its contextUsage describes the current context rather than consumed work. These are different aggregation problems from decoding one model response.

    The existing agent probes mostly constrain turns and tools and contain historical zero defaults for missing usage. Treat those as findings to review, not current accounting guarantees. Known zero monetary charge never proves zero token work. Use current Resources reports at the author boundary rather than copying their historical author Usage spelling or silently changing old capture claims.

    Keep the existing Responses lesson and openai==2.54.0 notebook as a lightweight control: an agent-oriented recipe must not complicate a single model call. A new direct Anthropic Messages wrapper is unnecessary for this study.

    The existing experiments/_live_support/accounting.py is a supporting reference. It already consolidates exact decimal conversion and a paid-call boundary, but its experiment policy requires a bill. The lesson allows spend_micros=None. Do not merge these policies or import this experiment module into core or the downloadable lessons as a shortcut.

    Meta-Evolve concurrency, a generic agent runtime, provider registries, pricing services, package publication and historical-capture migrations remain outside the comparison. Pi accounting findings can inform the separately planned SoL-Pi experiment;

    337 does not implement its mechanisms or depend on its live campaign.¶

    Common agent task and execution boundary¶

    Use a small temporary workspace with an editable text artifact, fixed task instructions and independent Python checks. Each agent must read relevant files, perform a permitted tool action and produce a candidate that the wrapper can extract. A success fixture includes multiple model steps and a tool result; disabling every tool and asking for one string cannot satisfy the agent gate.

    Exercise both roles: an agent proposes an artifact for independent grading; an evaluator runs an agent against a fixed task and grades its artifact or trace. Agent self-reported success is never the metric. Preserve the development/final split and declare which authorized Meta-Evolve feedback reaches the agent.

    Use fresh workspaces and sessions per independent attempt, with explicit runtime settings, tool/permission bounds and resource-loading policy. Check that project or user configuration cannot silently alter the fixture. A continuation/resume scenario separately tests attribution to the current invocation; it must not charge prior history again. SDK session IDs do not replace Meta-Evolve lineage.

    What the author must still own¶

    Responsibility Study treatment
    Request settings, credentials, model, SDK and runtime identity Remain in client construction and Task.environment; record permission, tool, session and resource-loading settings without credentials.
    Events, token categories and accounting scope Remain SDK-specific; declare deltas versus cumulative totals, duplicate identities, resets, disjoint categories and included auxiliary work.
    Output validity and grading Remain explicit in the wrapper and independent evaluator; an accounting utility cannot decide a score or candidate acceptance.
    Billed versus estimated cost and its source Remain explicit; a price calculation is evidence, not a bill.
    Exact conversion and accounting assembly Candidate reuse seam, subject to the comparison below. Reuse Resources validation/addition rather than inventing a second accounting type.
    Process/session lifetime, timing, retries and cancellation Wrapper retains SDK lifecycle and policy; a budget outside the callable is not a proven hard limit on its internal model/tool loop.
    Tool access and partial-work aggregation Preserve tool outcomes, terminal status, receipts and authorized feedback. Custom experience tools delegate to the existing audited reader.
    Request journal and final-check separation Remain journey-owned; these persist observations that may never reach a history commit.

    One minimal candidate¶

    First establish working baselines for all three agents, with explicit guarantees. Do not make the new baseline deliberately verbose to favor the candidate. Retain the short notebook's unknown-spend path as a simplicity check; it must not acquire mandatory billing setup merely to use a shared recipe.

    The initial hypothesis is an example-owned recipe for retaining observations and finalizing one agent invocation. Each wrapper interprets its own events first. Only then prototype one small shared function for the repeated accounting assembly, if the inventory supports it: explicitly scoped token work, elapsed work, cost provenance and partial receipts become existing Resources and EvidenceDraft values, or an accounting-unknown escape. Do not force streams into a universal event schema, a new public receipt class or a result hierarchy. The exact seam is provisional; a final-number formatter alone may earn no helper.

    Meta-Evolve proposer or evaluator
    -> user-owned Codex / Claude / Pi invocation
    -> native model/tool/session events and final artifact
    -> wrapper-owned attribution and failure classification
    -> candidate accounting seam -> existing Resources + evidence + result

    The wrapper still encloses startup, iteration, tools, terminal decoding and cleanup in the work-accounting boundary. A function called only after success cannot recover a lost stream or discover unreported internal calls. The candidate neither imports an SDK nor dispatches requests, retries, fetches prices, grades output, adds engine counts, or supplies missing measurements.

    Keep ProposalResult and EvaluationResult at their current owners. The study must exercise both roles; returning a provider's self-assigned score cannot replace the independent evaluator. If reuse requires callbacks for every field, provider modes, or a generic adapter protocol, record that as evidence against this candidate rather than enlarging it during the study.

    Deterministic evidence matrix¶

    Run applicable cases before and after for all three targets, then through real Meta-Evolve callables, storage and budgets. Native transports/parsers must be exercised where the SDK is used, with scripted process or model responses; Pi's RPC probe also exercises its pinned runtime against deterministic model/tool fixtures. A fake complete() result alone proves only reducer logic. Record adapter-level and runtime-level evidence separately, including telemetry gaps. Use controlled clocks and synthetic billing strings; no paid calls are needed.

    Case Required observation
    Completed tool-using agent, proposer and evaluator Correct artifact or independent metric; equivalent resources, evidence and engine counts before/after. Multiple internal model steps do not become Meta-Evolve trials/evaluations.
    Cached and reasoning categories Follow each pinned runtime's disjoint/subset rules; preserve breakdowns without adding them twice.
    Repeated events, final totals and per-model breakdown Count each execution once; never add a final aggregate to the steps it summarizes. Duplicate text/tool events are not additional billed calls.
    Continued/resumed session and reset Attribute only this invocation's work. Apply verified delta/cumulative/reset rules; retain prior receipts without charging them again.
    Compaction, internal retries and nested agents/tools Include observable auxiliary work once, preserving attribution. If required work is unobservable, expose the gap rather than calling a partial total complete. Do not fabricate an equivalent capability in another runtime.
    Wrong completed answer Measured low score under the declared grader, not an infrastructure failure.
    Empty, incomplete, malformed or unsupported artifact with known usage Typed failure without a score; keep tokens, bill if known, elapsed work and diagnostic evidence. Final assistant text alone is not proof the artifact is valid.
    Tool failure, permission denial or exhausted turn limit Preserve native terminal status and costs. A recoverable tool error can precede a valid final artifact; an unsuccessful overall execution has no invented score.
    Cancellation, timeout or process death mid-tool/stream Retain completed-prefix receipts, stop/close the owned process or session, record incomplete work and do not promote a partial artifact as success.
    Failure proven before dispatch No model/tool work dispatched and no invented paid usage; distinguish this from an ambiguous process or transport error.
    Transport failure after possible work, unusable body, or missing required accounting ExecutionAccountingUnknown escapes; available receipts and cause survive; no fabricated zero or automatic retry.
    Missing/null/negative/boolean token category Follow the pinned provider contract; absent required counts escape. Never turn absence into zero by convenience defaulting or lose a bad component inside a valid sum.
    Exact bill, explicit zero, fractional micro and high-precision amount Count billed spend exactly under the existing round-up rule; preserve raw amount/source. Reject lost float precision rather than claiming to reconstruct it.
    Tokens known, bill absent or estimate only Successful output stays usable; spend is None, estimates remain evidence. SDK-reported dollar fields alone do not establish a bill. A monetary ceiling stops subsequent work under shipped rules.
    Independently established no per-invocation charge Explicit zero spend is valid only with that basis recorded. A subscription label or absent cost field alone is insufficient; missing required tokens still escape.
    Optional billing lookup fails Preserve model output and known resources; record unknown spend and a safe diagnostic. Distinguish an unavailable bill from an exception announcing unknown required work.
    SDK retry controls and explicit caller retry Record actual runtime retry policy and observed attempts. Disable retries for the basic fixture where supported; test internal retries separately, exposing unobservable work or an unavailable control.
    Later decoding error after usage was recovered Preserve already known costs in a typed failure or available receipt; never fall through to an ordinary exception that books zero usage.
    Multiple requests, then known failure Aggregate completed and failed-request resources once; retain partial evidence, with no invented full-suite score.
    Multiple requests, then unknown accounting Keep completed-prefix receipts plus available failing-request facts; no fabricated complete result or charge. Distinguish the journal from committed history.
    Nested run Forward inner.usage().resources once; do not forward inner engine counts. Add only outer work not already represented in the nested resources.
    Timing and post-run inspection Include the declared invocation/cleanup work once; overlapping tool/model durations are evidence, not extra outer elapsed time. Reading history invokes neither SDK nor cost callback.
    SDK limits versus Meta-Evolve budget Demonstrate the actual enforcement boundary; do not claim an outer admission check interrupts in-flight agent work or that an estimated SDK cost cap is a billed-spend ceiling.

    For partial and nested cases, test known-plus-known and known-plus-unknown spend. The journey's request journal overlaps committed history; adding their totals would double count. Final evaluation remains outside development usage and feedback. The helper does not add a new durable unknown-token representation.

    For features unavailable on one target, document the native limitation and verify honest rejection or incomplete accounting. This does not waive the shared tool-using success, interruption and attribution cases. An SDK with insufficient telemetry can be a valid finding against a reusable helper, not a passing claim of complete accounting. No new durable accounting model is implied.

    Baseline bugs are findings, not behavior to preserve. Use canonical contracts as the oracle and record any mismatch separately before claiming equivalence. Do not silently fix a production wrapper inside the comparison and attribute that correction to the helper's ergonomics.

    Three reviewable steps¶

    Step Work Exit evidence
    1. Freeze and reproduce Pin SDKs, bundled runtimes, Pi/Node and transport dependencies. Adapt existing Codex/Claude probes to the common agent task; add Pi RPC. Inventory native usage scope and the simple Responses control. Three offline baselines, native event traces, required author decisions and baseline defects/telemetry gaps.
    2. Compare one candidate Keep SDK lifecycle/extraction local; test one shared accounting seam against all three. Run tool, interruption, partial/nested and attribution cases through real storage/budgets. Keep fixture facts identical across arms. Before/after source and event-to-resource traces, both callable roles, repeatable outcomes and documented unsupported cases.
    3. Decide and hand off Review correctness first, then the friction scorecard. Choose retain, recipe/example-local reuse, defer, or public-helper follow-up. A decision with evidence, remaining costs and rejected alternatives; input for #269 and the #330 parent.

    When executed, keep the runnable comparison under experiments/sdk_accounting/, with a small README, pinned optional dependencies, deterministic fixtures and focused tests. Create files as each responsibility needs them, not a destination package tree. Keep hand-written files normally below 300 lines. Use a separate environment so study SDKs/runtimes do not enter core dependencies or change the lesson's installed SDK baseline. Block external traffic in the fixture harness; use controlled temporary workspaces and isolated agent configuration.

    Write actual results to docs/project/sdk-accounting-study.md when they exist; link it from this plan and the practical-journey handoff. Retain exact commands, source SHA/dirty patch, Python/Node/SDK/runtime versions, fixture identity, outcome counts and representative traces. A skipped integration is not comparison evidence. The first implementation's record separates native SDK shape checks from scripted agent execution and the remaining runtime work.

    Friction scorecard and decision rule¶

    For each agent integration, retain a side-by-side worksheet with:

    • Decisions the author must understand before and after, identifying which were eliminated, merely relocated, or still essential provider semantics.
    • Repeated validation, monetary conversion, evidence construction and failure branches removed, including the shared implementation and its configuration in the code-size comparison. Shorter call sites alone are insufficient.
    • Concepts and indirections added, including how an author locates a bad token field, distinguishes unknown spend from free work, and diagnoses partial work, session attribution or process cleanup. Include Pi's language/process bridge.
    • Edits needed to change tool permissions, session policy, an artifact check, billing reporter or agent runtime. Keep these as concrete edit traces, not ratings unsupported by examples.

    All accounting/failure gates must pass before a benefit counts. Favor a maintained recipe or example-local function if it removes recurring error-prone work across the three agents while leaving required decisions visible. Report a narrower benefit as narrower support, not universal agent compatibility. Reject a candidate that simply renames constructors, moves the same branches behind hooks, requires provider special cases, or complicates the notebook's unknown-spend path.

    Disposition What closes the study
    Retain existing wrappers Evidence shows insufficient shared work or greater complexity; record the best recipe and why a helper was rejected.
    Recipe or example-local reuse Name its owner and bounded supported cases; describe the concrete migration and verification needed without promising a public import.
    Defer helper adoption Complete the bounded comparison, then name the additional evidence or SDK capability needed to revisit adoption. An unfinished required baseline is not a completed study.
    Public helper warranted Open a separate implementation issue specifying the proposed contract, placement, compatibility/release gate and migration tests. #337 alone authorizes no public helper shipment.

    Keep findings with the existing #269 accounting review and #330 coordination. Fixture results establish accounting behavior; author edit traces support an engineering usability judgment. Neither substitutes for live-provider evidence or the independent newcomer sessions.

    Difficulty and completion boundary¶

    This is a medium-to-high difficulty study, larger than comparing two text APIs. Most effort is in lifecycle, tool/stream failures, cumulative attribution and SDK telemetry gaps. Start with Codex and Claude, then require Pi's different process/session boundary before the final decision. Reuse existing fixtures; estimate any public helper and its maintenance separately after the evidence.

    The original full-study gate required all three agent integrations to have before/after evidence and every applicable matrix case resolved. The accepted lightweight scope instead closes #337 with three reporting comparisons, focused failure/accounting checks, runnable recipes, and a retain-local-reuse decision. The decision record identifies the evidence and deferred runtime cases; it does not claim that the full matrix passed. No model-quality improvement, easier onboarding, or live reproducibility is claimed from these deterministic checks.
