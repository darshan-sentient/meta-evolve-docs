    Run summaries without a winner: implementation plan for #317¶

    Status: Design—not shipped.

    This planning record is retained for design history. The implemented source contract now belongs to the programming model, with verification tracked separately.

    Prepared September 18, 2026 for #317, under #313. The summary contract owns the proposed behavior; this page specifies its implementation and tests. The programming model and architecture remain the shipped contract owners.

    Starting point and release boundary¶

    The inspected HEAD is c04ec6b4b949b8a2702779107e25acd24feb8020, with local #297,

    314, and #315 work. #316's callback implementation began changing during this¶

    review. Preserve those edits; identify the actual integration revision before implementation and reconcile callback fixtures with the accepted #316 contract. This plan changes no runtime source or tests.

    The local #314 foundation decision and Author API revision gate now freeze the summary, comparison, CLI, and pending-seed contracts. They select a coordinated pre-1.0 compatibility reset, working target 0.2.0. Bind implementation to the reviewed foundation revision and finalize the constructor/private seams below in its handoff. Other API redesign implementations are not prerequisites.

    Keep #317 as one focused implementation PR with query behavior, consumers, tests, migration guidance, and canonical documentation. It changes reporting, not execution, search, budget admission, or M11 concurrency. Do not combine it with callback migration or opportunistic namespace cleanup.

    Findings that determine the design¶

    Source tracing and deterministic probes establish:

    Current behavior Consequence for #317
    A successful summary() performs four validated loads; compare() performs ten across its two runs. Build each summary and its comparison inputs from one captured event frontier.
    A failed seed with one evaluation, two tokens, and seven billed micro-USD raises from summary, both before and after stop. Make reporting independent of rankability without hiding cost.
    All four lifecycle/rankability combinations occur through ordinary Session.start() and stepping. Test real execution boundaries without truncating event streams.
    Distributed Session.start() can retain the seed while its evaluation is pending. Summary raises; inspection and usage currently raise SearchNotStarted. Committed-usage reporting must not require a ready policy view.
    Failed-left/missing-right comparison raises NoSuccessfulEvaluation before reading the right side. Keep left-to-right failure precedence when summaries stop raising.
    Missing summary raises generic RunError; inspection raises RunNotFound. Deliberately align missing-summary behavior with the typed read boundary.
    CLI run failure produces exit 1 and only an error line. Preserve exit 1 while making the actual summary available on stdout.
    Browser detail already uses inspection; comparison consumes strict RunComparison. Preserve those routes and refusal behavior; no new summary endpoint is needed.

    The source-hashed probe and output are in /private/tmp/meta-evolve-317/probe.py and probe.json. These observations are baseline evidence, not a result for the proposed implementation.

    1. Freeze the public record and invariants¶

    Retain RunSummary as the same root-exported, frozen, slotted application view. It remains outside durable serialization. Preserve its current field names, decoded seed/lineage values, provenance, and count/resource meanings.

    Change Required meaning
    Add lifecycle complete iff a committed stop exists; otherwise incomplete
    Add rankability rankable iff a successful primary-objective measurement is selectable
    Add stop_reason The recorded reason when complete; None when incomplete
    Change primary_score to int \| float \| None Actual selected measurement or None; zero and negative scores remain valid
    Permit empty winning_lineage Empty iff unrankable; otherwise the existing decoded causal lineage

    Make the three new fields required keyword-only fields, without defaults that would guess the lifecycle of a manually constructed record. Preserve the binding order of existing positional fields; callers constructing summaries directly add the new keywords. Run.summary() itself gains no parameter.

    Validate the new relationships in RunSummary.__post_init__: accepted state values; non-empty string stop reason iff complete; finite numeric, non-boolean score and non-empty tuple lineage iff rankable; None score and empty tuple lineage iff unrankable. A rankable summary must have at least one completed evaluation. Type errors and contradictory values should fail clearly. Do not try to authenticate arbitrary user-constructed history or compare decoded artifact objects merely to validate these relationships.

    evaluation_count continues to count committed evaluation outcomes, including failed evaluations and the seed when evaluated. Pending evaluations do not count. Proposal attempts, bootstrap records, and worker deliveries remain distinct. Keep usage, experience totals, and name_only_components unchanged. Do not add an improved flag: selecting a seed or an exact tie is still rankable.

    Keep best(), best_trial(), and default lineage() strict when nothing ranks. Detailed typed failures remain in inspect()/trials(); a compact summary does not become a second full inspection aggregate.

    2. Build from one validated snapshot¶

    Keep summary/comparison ownership in application/comparisons.py unless the final size requires a responsibility-based split. Use a private load/build seam so summary() and compare() reuse the same projection and seed metadata:

    1. Call load_validated_run(..., require_existing=True) exactly once for this run. A nonexistent run raises RunNotFound; corrupt nonempty history keeps its existing typed integrity failure.
    2. Use the retained declaration and ViewBuilder for primary ranking, seed decoding, and causal lineage. Handle only the expected absence of a successful evaluation; do not catch corruption, decoding, or infrastructure failures.
    3. Derive lifecycle from projection.stop, not from score, budget, or a live Session object. Preserve ranking direction and stable logical tie order.
    4. Aggregate recorded usage/experience and build the storage-independent value. It must remain usable after storage closes, including custom-codec values.

    Do not call public best(), lineage(), or inspect() inside this builder. They would trigger fresh loads or construct unrelated detailed views. Reusing the existing ViewBuilder retains ranking and lineage semantics without a new query framework or public snapshot object.

    One snapshot means one validated event frontier per run. It does not promise an atomic transaction across two independent stores. The browser already checks versions before and after comparisons; preserve that stronger UI behavior.

    Include the pending seed evaluation¶

    Use an actual admitted Session.start(..., mode="distributed") fixture. Before driving it, its valid genesis contains one seed trial and zero evaluations; summary should be incomplete/unrankable, with no score, stop, or winning lineage. Preserve its decoded seed and aggregate only committed usage. Pending external work is not an estimated or settled cost.

    RunProjection.search_state intentionally rejects this frontier. Keep that execution guard. Separate the existing recorded-usage fold from its readiness requirement with one small private helper, reusing SearchState.usage's exact calculation/order. Share it with the summary and, as a bounded supporting fix, Run.usage() and inspection's usage field so those read paths agree on this valid state. Do not add a scheduler path, force bootstrap execution, duplicate numeric aggregation, or return guessed zero usage on a caught exception.

    Normal bootstrapped usage must stay exactly equal, including unknown spend, post-call overages, failed work, and floating-point elapsed-work aggregation. The policy-facing view's readiness and recovery rules remain unchanged. Record the newly supported pre-bootstrap inspection/usage case in migration guidance.

    3. Preserve strict comparison and error order¶

    Perform these steps in order, reusing each side's loaded inputs:

    1. Validate that other is a Run.
    2. Load/build the left summary and require a successful measurement.
    3. Load/build the right summary and require a successful measurement.
    4. Apply the existing declaration-compatibility checks in their existing order.
    5. Compare actual numeric scores using the primary objective's direction and return the existing comparison record.

    This uses at most one validated load per side and short-circuits before reading the right run if the left is unrankable. A missing/corrupt left side still wins over a failed right side; an unrankable side still wins over declaration incompatibility. The deliberate missing-run change is the more specific RunNotFound, which remains a RunError.

    Retain evaluator, artifact kind, metric/direction/threshold, task/effective budget, seed representation/schema/digest, and authorized-proposer controls. Random seed and context/experience differences remain reported separately. Do not add a requirement that a rankable run has stopped, or relax proposer equality to compare different improvement procedures.

    Harden direct RunComparison construction for the newly optional scores: both sides must be rankable; winner is None means equal successful scores, never two missing scores. An explicit winner must still be exactly one of the two summary instances. Preserve existing consistency checks for comparison flags. Correct objective direction stays the builder's responsibility; adding another objective field solely to re-prove it in the record is unnecessary.

    4. Migrate reporting consumers¶

    Keep _render_summary() as the one text formatter. Add lifecycle, rankability, and stop rows; render an absent score and empty winning lineage explicitly (for example none). Continue omitting measured wall-clock values from stable CLI text. Render zero/negative scores as scores, not as absence.

    The CLI needs text and exit status together. Use one small private command report value with those two fields, and let main() remain the only stream writer. A shared summary-report helper can choose status from rankability; do not use an exception to carry an ordinary unrankable report or execute a second query just to choose the exit code. Other commands retain their existing output/status semantics; no new public CLI result type is introduced.

    Command outcome stdout stderr / exit
    run/resume, rankable, including seed-selected Summary Empty / 0
    run/resume, unrankable Summary with state, absent score, and recorded cost Empty / 1
    inspect, valid rankable or unrankable history Detailed inspection Empty / 0
    compare, compatible rankable histories Comparison Empty / 0
    Missing/corrupt run, inadmissible resume, or refused comparison No fabricated summary Existing typed error / 1
    Usage/module error Existing usage behavior Existing error / 2

    Unexpected defects keep their traceback. Keep factory compatibility, parser flags, UI server lifecycle, and capability decisions out of this change. Update AST boundary tests narrowly: allow the shared status helper to read rankability for control flow, while formatting remains confined to the existing renderers and stream writes remain confined to main().

    Browser detail already displays lifecycle/rankability through RunInspection. Test the new pending-seed case there through the shared inspection fix. Strict comparison still returns HTTP 422 for an unrankable side; preserve escaping, inert artifact presentation, version checks, and cache behavior. No new route, report format, or browser-specific summary semantics is needed.

    5. Regression and compatibility matrix¶

    Prefer focused new test_run_summaries.py and CLI outcome coverage over growing the already-large comparison/CLI suites. Reuse existing fixtures and failure injection. Normally keep files below 300 lines; preserve the CLI's documented single-boundary exception and review any necessary exact length-ratchet update.

    Case Required evidence
    Four lifecycle/rankability states Create through public sessions; state, stop, optional score, lineage, counts, and usage agree with inspection
    Pending distributed seed Real admitted start; zero evaluated outcomes, truthful committed usage; reporting executes no work
    Seed-only, tie, regression, maximize/minimize Selected measurement and lineage match strict queries; zero and negative scores remain present
    Failed proposer/evaluator; unevaluated successor Typed outcomes and spent resources survive; no score is invented
    Unknown spend and overages Summary/usage/inspection agree and never coerce unknown to zero
    Feedback and custom codecs Declarations/provenance/experience totals and decoded seed/lineage types remain intact
    Snapshot coherence One validated load per summary, at most one per comparison side; a commit after the captured frontier cannot mix old counts with a new winner
    Query purity No proposer/evaluator/search execution, event append, work claim, store migration, or durable mutation during reporting
    Strict comparison Failures on either/both sides, error precedence, incompatible controls, cross-store comparisons, exact tie, and winner identity
    Record construction Invalid states/combinations fail; required keyword-only additions and dataclass immutability are intentional
    CLI and browser Real subprocess output/exit tests and existing browser refusal/security/cache tests, including pending seed
    Historical stores Old success/failure/incomplete histories produce new views without rewriting records or relaxing resume verification

    Reuse tests/_faults.py for interrupted durable prefixes rather than deleting SQLite rows. Reuse the old stores identified by #314's compatibility record, with their source and capture hashes. Hash stored records/artifacts before and after reads, and test matching-runtime resume separately from expected cross-version manifest refusals. Add no durable type, event field, store-schema version, or identity input for a derived summary.

    Compare affected component manifest digests before and after any shared-source extraction. A reporting change is not proof of resume compatibility: preserve exact-source checks and record any fingerprint effect separately from schema compatibility and from #316's invocation changes.

    Update existing tests that explicitly require summary failure, especially test_run_comparisons.py, test_monetary_accounting.py, and test_api_reference_examples.py. Their cost and strict-winner assertions must remain; replace only the obsolete summary expectation. Preserve existing custom codec reopening and artifact/source corruption tests at the read boundary.

    6. Documentation, implementation order, and completion¶

    Update Run, Run.summary(), Run.usage(), and RunSummary docstrings; the programming model/architecture; result inspection and CLI guides; budget guidance that currently warns against summary; and the executable failure reference case. Keep full failure diagnosis in the inspection lesson. Audit example reporting for optional-score assumptions without gratuitously rewriting successful-only studies or changing their algorithms.

    Migration explains: absence now returns primary_score=None; strict winner queries still raise; direct constructors require the new keywords; missing runs use RunNotFound; unrankable CLI runs print a summary and exit 1; and pre-bootstrap usage/inspection becomes available. Do not advertise a successful summary call as successful evaluation, improvement, or resumability.

    Implement in this order: record/constructor contract → shared recorded-usage and snapshot builder → strict comparison → CLI/browser consumers → canonical docs and executable examples. Each stage keeps its focused tests with the behavior. Review the combined diff as one #317 slice.

    Run focused summary, inspection, comparison, accounting, reopening, CLI, and browser checks first. Then run applicable runtime CI and the maintained Docs workflow, including strict build, rendered reference, executable examples, and fresh installed-package downloads. Identify the final source/lock/package and record actual results and limits. #318/#319 own coordinated release/publication.
