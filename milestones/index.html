    Meta-Evolve Milestones¶

    Purpose¶

    This roadmap grows Meta-Evolve through small, testable vertical slices. Every milestone must produce a runnable demonstration, preserve the contracts established by earlier milestones, and add only the infrastructure required by its acceptance tests.

    The first product target is a local, extensible improvement system in which a user can define an artifact, task, evaluator, proposer, search policy, and context policy; run a bounded experiment; let agents inspect prior work; replay or resume the run; and compare results under equal budgets. Harness evolution, meta-evolution, trusted concurrency, and federation build on that local product.

    The harness-evolution demonstration (milestone 8) is the flagship product demo — "point this at your agent and eval set, get a measurably better agent, and inspect exactly why each change was kept." Earlier milestones should keep that demonstration in view rather than treating it as a distant capstone.

    Before the numbered milestones, a disposable API spike validated the user-facing interface against both deterministic code and a real model. The spike is a design probe, not a shortcut into the durable implementation. It is complete; see its status below.

    Development rules¶

    1. Every milestone has one canonical example that runs with a documented command.
    2. Every new port has an in-memory or deterministic reference adapter and a conformance suite.
    3. The coordinator contains no branches for particular artifact types, proposers, evaluators, or search policies.
    4. Durable behavior is specified through domain events and observable results, not adapter internals.
    5. New infrastructure is introduced only when a milestone's proof requires it.
    6. Failures remain typed: poor task performance, invalid output, timeout, resource exhaustion, policy violation, and infrastructure failure are not interchangeable.
    7. Tests are deterministic by default. Tests requiring credentials, network access, or hardened infrastructure are explicitly separated.
    8. Each milestone updates examples, tests, and user-facing documentation together.
    9. The programming model is the canonical public API contract; other documents link to it rather than redefining signatures.
    10. Canonical examples are first-class user-facing documentation, not test fixtures: each must be short, copy-pasteable, and runnable from a clean checkout, and the simple callable path never requires or surfaces kernel vocabulary such as Trial, OperatorSpec, or WorkItem.

    Pre-milestone API spike¶

    Status: Shipped (July 16, 2026). Both demonstrations ran through the same small public surface under experiments/00_api_spike/, including a real gpt-5.4-mini Codex SDK prompt-optimization run. The exit gate passed: findings are recorded in real_model_findings.md and folded into the programming model's evidence section. Closed by #23.

    Goal¶

    Exercise the smallest declarative API before durable domain models and package boundaries are fixed.

    Demonstrations¶

    Build a disposable one-to-three-file implementation that runs:

    1. deterministic integer improvement with Greedy and BestOfN;
    2. one real-model prompt-optimization task whose proposer and evaluator each require only a small user function.

    The spike should test the canonical Task, meta.run, proposer, evaluator, search, and Run.best()/lineage() surface from the programming model.

    Questions it must answer¶

    • Can a plain callable be used as a proposer and evaluator in local mode?
    • Is the distinction between task, seed, proposer, evaluator, and search obvious in working code?
    • Does changing search policy require no change to task or proposer code?
    • Can failures and multi-metric evaluations be represented without exposing orchestration machinery?
    • Which values must become durable records, and which abstractions are premature?

    Exit gate¶

    • Both examples run through the same small public surface.
    • The programming model is revised from observed use rather than aspiration alone.
    • Any deliberately unsupported capability is named explicitly.
    • None of the spike's internal structure becomes a kernel contract without Milestone 1 justification.

    Out of scope¶

    Replay, crash recovery, ports and adapters, stable schemas, experience grants, workspace isolation, provider portability, and production-quality model integration.

    Common definition of done¶

    A milestone is complete only when:

    • its canonical example runs from a clean checkout;
    • its acceptance tests pass locally and in CI where the required capabilities are available;
    • events, artifacts, evaluations, and policy decisions retain causal lineage;
    • public contracts and durable schemas are documented and versioned;
    • newly added adapters pass their conformance suites;
    • resource use and failure outcomes are observable;
    • no later-milestone infrastructure was added speculatively;
    • the next milestone can build on the result without replacing the kernel.

    Milestone 1: deterministic kernel¶

    Status: Shipped (July 21, 2026; #1, #32). The canonical number search, exact budget accounting, retained-event projection rebuild, built-in Greedy decision reproduction, failure replay, and the remaining acceptance tests now pass. Restart and resume were deliberately deferred to, and are now shipped by, Milestone 4.

    Goal¶

    Prove the smallest complete improvement loop without language models, subprocesses, databases, or distributed workers.

    Canonical demonstration¶

    An integer artifact begins away from a hidden target. Deterministic proposers add or subtract fixed values, a pure evaluator rewards proximity to the target, and a sequential coordinator runs until its evaluation budget is exhausted or the target is reached.

    select parent
  → allocate bounded work
  → produce proposal
  → create successor artifact
  → evaluate with evidence
  → append events
  → update projected state
  → choose the next action

    Deliverables¶

    • Frozen, serializable domain models for tasks, artifacts, proposals, trials, trial outcomes, evaluations, evidence, budgets, usage, policies, and typed events; a work-item delivery record stays internal to the kernel and out of user-facing types.
    • Opaque typed identifiers and schema versions on durable envelopes.
    • In-memory artifact and event stores.
    • A deterministic callable proposer adapter and pure-function evaluator adapter.
    • A sequential coordinator that validates transitions, authority, and budgets.
    • A minimal SearchProgram.next(state) decision contract; remaining budget is part of projected state.
    • Typed OperatorSpec values produced by operator policies rather than durable raw strings.
    • Logical ordering, deterministic tie-breaking, and recorded named random substreams.
    • examples/learn/number_search/ with a documented run command.

    Expected behavior¶

    • The same task, initial artifact, policy, seed, and budget produce the same logical decisions and final projected state.
    • Every artifact and evaluation can be traced to the trial, proposal, and search decision that caused it.
    • Trial identity remains distinct from duplicate delivery or completion attempts.
    • Duplicate completion is idempotent.
    • Exhausted budgets prevent additional work.
    • Invalid proposals and evaluator failures are recorded without being treated as low scores.
    • The run can be rebuilt from its event stream without agent-local state.

    Acceptance tests¶

    • Reachable and unreachable target scenarios.
    • Exact evaluation and usage accounting.
    • Deterministic replay from an empty projection.
    • Decision reproduction with the same named random substreams and trial seeds.
    • Optimistic append conflict in the in-memory event store.
    • Duplicate work completion.
    • Invalid transition and budget-exhaustion rejection.
    • Failure taxonomy serialization and replay.

    Out of scope¶

    SQLite, filesystem persistence, subprocesses, real agents, semantic search, snapshots, concurrency, and user interfaces beyond the example command.

    Milestone 2: replaceable search policies¶

    Status: Shipped. M1 supplies the Greedy baseline and the generic preparation boundary. M2.1 adds durable archive decisions, linked decision explanations, and the first reusable policy-contract gate. M2.2 adds the public BestOfN(max_trials=20) preset, independent seed expansion, and historical decision reproduction through the same contract. M2.3 adds the public Population(size=3, tournament_size=2, max_trials=20) preset with explicit rank-ordered archive membership, deterministic tournament selection, and a corridor test showing retention of a temporarily worse branch. M2.4 adds strict compatible-run comparison and the canonical equal-budget three-policy benchmark.

    Goal¶

    Prove that search behavior is a replaceable policy and that different policies can be compared fairly without changing the coordinator.

    Canonical demonstration¶

    Run independent best-of-N, greedy hill climbing, and a small population policy against the same integer task, initial artifact, seed rules, and evaluation budget. Produce a comparison report containing best score, evaluations, usage, and lineage references.

    Deliverables¶

    • Independent best-of-N policy.
    • The M1 Greedy baseline covered by the shared M2 policy conformance suite.
    • Small population retention policy.
    • Deterministic selection and tie-breaking rules.
    • Explicit admission, stopping, and budget-allocation decisions.
    • A run-comparison projection or report.
    • One publishable benchmark example: an honest, reproducible equal-budget comparison (for example, greedy with context reuse versus independent best-of-N) presented as a notebook or report a reader can rerun, serving as the project's first credibility artifact.
    • examples/learn/policy_comparison/.

    Expected behavior¶

    • Policies consume the same projected state and return typed decisions.
    • Replacing a policy requires no coordinator, runtime, evaluator, or storage changes.
    • Every policy decision records its inputs, policy version, rationale metadata, and observed logical step.
    • Comparisons normalize results by the same declared budget.
    • A policy cannot directly mutate projections or grant itself additional budget.

    Acceptance tests¶

    • All three policies pass one shared policy conformance suite.
    • Equal inputs produce deterministic decisions.
    • Tie cases have stable outcomes.
    • Population admission and eviction replay correctly.
    • A historical policy decision can be reproduced without future evaluations.
    • Adding a minimal test policy requires only implementing the policy contract.

    Out of scope¶

    Pareto archives, novelty search, islands, bandits, MCTS, learned allocation, and policy evolution.

    M2.4 completion¶

    Run.summary() and Run.compare() are immutable derived views over committed records. Fair comparison requires identical evaluator/proposer declarations, primary objective, task and effective run budgets, artifact kind, and initial artifact declaration and digest. Policy choice, policy configuration, and root seed may differ; exact primary scores tie without a usage or policy tiebreaker.

    The canonical examples/learn/policy_comparison/ sweep uses target 12, moves (-2, 1, 5), initial value 0, nine evaluations, eight successor trials, and root seeds 0 through 39. Its executed notebook reports complete score and usage distributions and representative star, chain, and tree-branch lineages, with an explicit small-illustration evidence disclaimer. The companion executed milestone_2_tour.ipynb introduces M2.1 through M2.4 from the public callable path before showing optional kernel-level inspection.

    Milestone 3: shared experience and agent-directed exploration¶

    Status: Shipped (July 24, 2026; #3). M3.1 adds the read-only temporal experience projection, M3.2 adds bounded replayable policy-pushed context, M3.3 adds audited, strictly-prior agent-pulled access, and M3.4 adds declared derivation, run-aggregate experience usage, memory-strategy comparison, and the canonical four-variant demonstration.

    Goal¶

    Make prior trials useful to later agents through both policy-pushed context and agent-pulled investigation.

    Canonical demonstration¶

    Agent A produces several failed trials. Agent B searches those trials, opens a relevant proposal and evaluation, compares siblings, and uses the observed failure to choose a successful transformation. The new proposal records the exact experience B observed and used.

    Deliverables¶

    • An in-memory ExperienceGraph projection with occurrence-based node, ancestor, child, inclusive-sibling, causal-leaf frontier, trace, and inclusive historical state_at queries.
    • A scoped, read-only ExperienceReader with exact filtering and traversal.
    • ExperienceGrant bounds for task, run, logical time, result count, context size, and resource use; identity and visibility remain single-user stubs.
    • ContextPolicy implementations for NoMemory, AncestorsOnly, and BestSibling.
    • Events for automatic context selection, experience queries, opened records, and comparisons.
    • Immutable ContextBundle records and exact query-result records, including ordering and truncation.
    • Stable references from observed experience into Proposal.derived_from.
    • examples/learn/experience_reuse/ covering push-only, pull-only, and combined access.

    Expected behavior¶

    • Agents distinguish experience that existed from experience they actually observed.
    • An as_of argument may narrow but never widen a work item's logical-time grant.
    • Cross-task, out-of-run, retracted, or future experience is not returned.
    • M3.2 context selection obeys record and rendering bounds without consuming task usage; M3.3 pull operations count against their ExperienceGrant.
    • The derivation graph remains acyclic while semantic relationships may be typed cross-links.
    • Content deduplication does not collapse distinct causal occurrences.

    Acceptance tests¶

    • Agent B improves by consulting Agent A's recorded failure.
    • Push-only, pull-only, combined, and no-memory variants run under equal budgets.
    • Ancestor, sibling, and historical-state queries return expected results.
    • Attempts to cross task, run, or logical-time boundaries fail.
    • Query result limits and usage limits are enforced.
    • Replay reconstructs the same observed-context references and derived-from edges.

    Out of scope¶

    Embeddings, vector databases, learned retrieval, graph databases, filesystem projections, principal-based authorization, licensing enforcement, and cross-installation experience.

    M3.1 completion¶

    replay_experience_graph() derives one trial-centered node per committed trial occurrence through the validated run replay path. ExperienceRef uses the run, record kind, and existing occurrence identity; identical artifact payloads therefore remain distinct causal occurrences. Exact decision, explanation, proposal, artifact-creation, outcome, evidence, evaluation, and completed-trial records are retained without defining another lifecycle.

    Queries are scoped by task, run, and an optional inclusive logical step. Ancestors exclude self, siblings include self, frontier means visible causal leaves rather than archive membership, and a trace spans the target trial and its accessible ancestors while preserving committed event order with a fixed intra-event kind order. Missing, wrong-kind, cross-scope, future, hidden, retracted, and synthetic non-local direct targets all receive one opaque denial. Collection reads omit inaccessible occurrences and do not traverse through them.

    Only ExperienceRef is durable and exported through meta_evolve.domain. Graph and query views remain outside the package-root callable API. M3.1 adds no reader grant, pushed context, retrieval, durable graph store, authentication, licensing, or proposal-derivation contract.

    M3.2 completion¶

    meta.run(context=...) accepts NoMemory, AncestorsOnly, BestSibling, or a compatible declared policy. None and NoMemory() preserve pre-M3.2 identity, stream, trial specs, and proposer behavior except that the internal ProposerContext now exposes a synthesized empty bundle. Non-default configuration contributes one final serialized ContextSpec identity segment.

    ContextPolicyDeclared follows bootstrap evaluation. A transparent search-program wrapper stamps its policy reference only into successor specs, and a generic coordinator operation commits one ContextSelected after the decision explanation and before proposer invocation. Bundles snapshot exact typed records, stable reference order, canonical rendering, reason, truncation, and ContextUsage; record and character bounds are independent from task Usage.

    AncestorsOnly flattens accessible ancestors in graph-node and committed-record order. BestSibling excludes the current node, ranks only successful sibling evaluations through rank_evaluations, and preserves completion-order ties. Replay validates the committed records against their strictly prior visible sources and returns the committed bundle without rerunning selection or rendering. Context declaration and selection facts remain inspectable in the experience graph but cannot themselves become policy candidates.

    M3.3 completion¶

    meta.run(experience=...) accepts the run-level ExperienceAccess protocol; PullAccess(max_operations=20, max_results=20, max_records=100, max_chars=32_000) is the shipped declaration. None normalizes completely away. A non-default access declaration contributes the final serialized ExperienceSpec identity segment after any ContextSpec.

    Every successor receives a fresh immutable ExperienceGrant bounded to the same task/run and as_of=trial.logical_step - 1. Its ExperienceReader supports exact conjunctive search filters, open, ancestors, inclusive siblings, and right-minus-left numeric comparison. Results preserve committed ordering, exact structured snapshots, canonical prefix-bounded rendering, truncation, and cumulative operation/result/record/character usage. Failed evaluations remain inspectable and never become synthetic losses.

    The audited lifecycle is grant → (attempt → success|denial|exhaustion)* → proposal. Attempts charge before validation, opaque denials disclose no protected content, and over-ceiling calls receive a separate content-free exception. Replay validates authority, placement, reproducible operation identities, cumulative charging, and terminal matching, and holds every success to the shared deterministic contract: records must equal committed sources inside the effective boundary, references must stay visible, deltas must derive from the paired records, and rendering must prefix the canonical rendering of the committed records. Selection, traversal, filtering, and comparison logic is never re-run, and committed outcomes are returned directly. Context and pull-audit facts remain graph-inspectable but are excluded from both push and pull candidate sets, and naming them in a search filter is a malformed request. Pull usage does not change task budgets, logical steps, or named randomness.

    M3.4 completion¶

    Proposal and callable ProposalResult now carry an explicit ordered derived_from declaration. One shared pure validator reconstructs pushed and pulled observations from committed records and requires a unique, strictly-prior same-run subsequence. Resource exhaustion precedes derivation policy failure; both coordinator-imposed failures clear edges and commit no candidate. Valid typed proposer failures and failed independent evaluations retain their declared lineage.

    Canonical serialization omits empty derivation and rejects an explicitly encoded empty default, so old proposal, event, context, and replay bytes remain unchanged at schema version 1. RunExperienceUsage, Run.experience_usage(), and expanded summaries report context and pull totals. Comparisons continue to require equal task/run budgets and core declarations while allowing different memory strategies, with exact declaration-match flags.

    The runnable examples/learn/experience_reuse/ experiment gives no-memory, push-only, pull-only, and combined variants the same task, proposer, evaluator, chain search, seed, and task/run budget. It records early evaluator failures, then succeeds only when prior failure evidence is reused and cited. Replay reconstructs the same derivation edges. The companion executed milestone_3_tour.ipynb introduces M3.1 through M3.4 from the public callable path, with push_pull_lab.ipynb and derivation_comparison_lab.ipynb as focused kernel-level labs.

    Milestone 4: durable local runs and crash recovery¶

    Status: Shipped (July 24, 2026; #4, #47). Durable artifacts and events, atomic commit, verified manifests, corruption detection, migration, recovery-frontier replay, and context/experience-aware resume satisfy the acceptance gate without changing the M1–M3 logical identities or trajectories.

    Goal¶

    Persist the kernel without changing its logical behavior and prove that interrupted runs resume safely.

    Canonical demonstration¶

    Start a deterministic run, complete several trials, terminate the process, rebuild the coordinator and projections from disk, resume from the committed frontier, and compare the outcome with an uninterrupted run.

    Deliverables¶

    • SQLite append-only event store with optimistic concurrency.
    • Content-addressed filesystem artifact store.
    • Durable run, trial, population, work-item, usage, and experience projections.
    • Stable idempotency keys and committed logical steps.
    • A resume command or documented API.
    • Migration/versioning strategy for durable schemas.
    • examples/operations/crash_recovery/.

    Expected behavior¶

    • SQLite and in-memory adapters satisfy the same event-store contract.
    • Identical payload bytes reuse content identity while occurrence provenance remains distinct.
    • Only atomically committed object records and transition events affect reconstructed state.

    Goal¶

    Demonstrate genuine multi-generation evolution through two concrete, replayable search policies: GEPA-style per-key frontier evolution and UCT-style tree allocation with best-descendant backup. Both must pass the existing search-program conformance suite and outperform the appropriate baseline on deterministic, equal-budget fixtures.

    Specialists and TreeSearch are the shipped canonical names for per-metric specialist retention and value-directed tree allocation. Both use the policy namespace rather than adding a root export:

    from meta_evolve.policies import Specialists, TreeSearch

Specialists(
    metrics=("case:0", "case:1", "case:2"),
    max_trials=20,
)

TreeSearch(
    max_trials=100,
    exploration=2**0.5,
)

    BestOfN remains the one-generation equal-budget sampling control. M9.5 does not reopen the closed novelty, surrogate, or plateau-escalation proposals in #16, #17, or #18.

    Contract boundary¶

    • Shipped default ranking, stopping, and incumbent selection use Task.objectives[0]; successful evaluations may retain additional metrics.
    • Specialists binds a fixed ordered metric-key tuple. Every successful candidate must contain each configured key; extra metrics are ignored and a missing key is invalid search history.
    • Archive membership remains authoritative. Existing records keep replaying; membership deltas may remove several members without a new schema version or removed_member_ids field. evicted_artifact_id is None for zero or multiple removals and identifies the member for exactly one removal.
    • Per-key winners, ownership weights, tree visits, subtree values, and normalization inputs reconstruct from durable history. M9.5 deliberately accepts derived-state recomputation cost instead of adding hidden caches.
    • Stable tie rules and named decision randomness make replay and cross-process reconstruction deterministic.
    • Failed evaluations remain typed outcomes: they never become frontier members or synthetic low tree rewards, though failed tree attempts still count as visits.

    Canonical demonstration¶

    M9.5.2 adds a focused deterministic scenario beside the existing scalar comparison: BestOfN, Population, and Specialists share the same task, seed, proposer, evaluator, root randomness, budget, and trial limit. Population evaluates then evicts an aggregate-weak per-case specialist; Specialists retains and expands it into the aggregate winner. The report pins score, lineage, parent sequence, evaluation and failure counts, and exact usage.

    M9.5.3 adds a separate deterministic delayed-reward scenario: Greedy and TreeSearch share the same task, seed, proposer, evaluator, root randomness, budget, and explicit trial limit. Greedy's incumbent selection follows the immediately attractive branch to a plateau; TreeSearch's fixed widening also materializes the weaker delayed branch, and deterministic UCT descent revisits and expands it into the winner. The report pins score, lineage, parent sequence, evaluation and failure counts, and exact usage.

    M9.5.4 adds one credential-free command, examples/learn/policy_comparison/advanced_search.py, that runs BestOfN, Greedy, Population, Specialists, and TreeSearch on both fixtures above under the same task, seed, proposer, evaluator, root randomness, budget, and explicit trial allowance, with equality verified pairwise through the existing Run.compare() gate. On the specialist fixture, capacity-matched Population evicts the aggregate-weak specialist that Specialists retains and expands into the aggregate winner 10, which equal-budget BestOfN never reaches. On the delayed-reward fixture, Greedy plateaus at the immediately attractive score 5 while TreeSearch revisits the weaker delayed branch and reaches its descendant 10. Every result's report pins primary score, lineage shape and depth, every selected parent, evaluation and failure counts, archive behavior, and exact resource usage; the other policy results stay visible without broadening either pair-specific claim.

    Replay equivalence is a conformance invariant. The milestone's behavioral evidence is improvement on these controlled equal-budget fixtures.

    Acceptance tests¶

    • Existing archive records replay, valid multi-removal transitions validate, and malformed membership deltas fail deterministically.
    • Frontier specialists remain selectable, one candidate may displace several obsolete members, missing dimensions fail, and extra dimensions are valid.
    • Frontier replay, resume, and cross-process reconstruction select identical parents.
    • Tree tests pin node selection, visit accounting, progressive widening, deterministic normalization, direction handling, and Q-value backup.
    • Failure-heavy tree branches remain representable without fabricated scores.
    • Both presets pass conformance, replay, and resume suites.
    • Both deterministic fixtures demonstrate the intended later-generation or delayed-reward advantage under equal budgets.
    • The unified five-policy comparison holds every external control equal within each fixture and reports complete structured evidence for every policy.
    • Examples, API references, guides, architecture, programming model, and implementation plan agreed before the status changed to Shipped.

    Out of scope¶

    Pareto archives, novelty search, islands, learned allocation, live-provider evidence, and extracting ParentSelector, Archive, BackupRule, or similar protocols. Revisit a shared protocol only after both concrete policies expose a repeated independently testable seam.

    Milestone 12: contributed and federated network¶

    Status: Design—not shipped. Tracked by #11 and dependent on M11's trusted-worker boundary.

    Goal¶

    Allow independent installations to contribute and exchange authorized agents, evaluators, artifacts, evidence, and experience subgraphs with verifiable provenance.

    Canonical demonstration¶

    Two Meta-Evolve installations exchange a signed, policy-filtered experience bundle. The receiving installation verifies identity and content, imports only authorized records, preserves source provenance and restrictions, independently evaluates a promoted candidate, and processes a later retraction.

    Deliverables¶

    • Signed manifests for contributors, agents, evaluators, tasks, environments, and artifact schemas.

    • Minimal dispute and reputation projections based on recorded evidence.

    Expected behavior¶

    • Import never grants broader access than the source export policy and receiving trust policy allow.
    • Missing private ancestors can be represented by verifiable redacted references without fabricating lineage.
    • Invalid signatures, digests, schemas, or causal references are rejected.
    • Imported evaluations are evidence, not automatic local promotion.
    • Retractions and permission changes identify dependent artifacts, datasets, skills, and checkpoints.
    • Operators may keep private events while publishing permitted claims and artifacts.

    Acceptance tests¶

    • Successful signed export/import between two installations.

    • Private, embargoed, and redacted source handling.
    • Conflicting evaluator results and independent verification.
    • Retraction propagation through derived records.
    • Duplicate import idempotency and schema-version negotiation.
    • Threat-model review covering code execution, evaluator collusion, poisoning, sybil behavior, reward hacking, and correlated replication.

    Out of scope¶

    Token economies, unrestricted peer-to-peer execution, global consensus, claims that containers alone secure untrusted code, and scientific validity without domain-governed evidence and replication.

    new use case

new use case
  ≠ coordinator branch
